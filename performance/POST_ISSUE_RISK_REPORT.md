# 出票后风控实现与性能对比

日期：2026-10-07。基线使用本次修改前的工作区构建，并非 Git HEAD 或历史报告。

## 实现

- 入口使用已有画像、黑名单、限流和本地规则，判定 PASS / REVIEW / BLOCK。BLOCK 当轮拒绝；PASS 和 REVIEW 正常交易。
- 仅 REVIEW 在落单事务中保存 ADMISSION 特征、命中规则和策略快照，复用 tb_risk_decision，无表结构变更。
- 落单仅创建 AUTO_PAYMENT 消息；出票事务成功进入 ISSUED 后，才为 REVIEW 创建 RISK_CHECK 消息。
- AI 调用使用入口快照和已出票的订单信息；不锁订单、不跨远程调用持有数据库事务。最终风险记录、画像和消息幂等记录在短事务内提交。
- 高置信度（默认 ≥0.8）、有理由的 HIGH 结论，由 Java 将画像判为 BLOCK；LOW 可解除疑似。其他情况保留有界调分，AI 不可用保留 REVIEW。
- 画像只在提交后发布到 Redis；缓存按版本防止旧写覆盖新写；有效 BLOCK 不被普通低风险结果降级，来源订单创建时间更早的结果不覆盖较新的画像。

## 环境与口径

- 独立 credit-risk-ab 容器，MySQL 8、Redis 7、RocketMQ 4.9.7；原有应用数据库和 Redis 未修改。
- Java 8，堆 -Xms128m -Xmx384m，SerialGC；Hikari 默认上限 10；前后使用同一运行镜像、同一线程池与配置。
- 32 个并发客户端，每轮 160 个不同用户、同一票档、每人 1 张；两种场景各重复三次。库存 1000，预热消耗 1 张，测量后应剩 839。
- PASS：关闭计分规则。REVIEW：只启用设备关联规则，使每笔规则分固定为 60。限流提高至测试负载以上，避免把拒绝吞吐当作成功吞吐。
- AI 为固定延迟 600 毫秒的本地测试服务，返回 MEDIUM / 零调分，用于隔离执行时序和资源占用；未验证真实 LLM 推理质量或真实调用耗时。
- 抢票 QPS = 160 / 从负载开始到全部抢票响应完成的墙钟时间。出票吞吐 = 160 / 从负载开始到观察到全部出票的时间；数据库轮询有约数百毫秒及进程启动开销。
- 每轮等待调查任务全部完成后再清理隔离数据，校验请求成功、订单数、出票数和库存。
- 旧 full-success 脚本主要用请求开始时间跨度计算 QPS，会漏掉最后响应的耗时；其历史 QPS 不可直接与此表比较。

## 正确性与测试

- 共 1920 笔测量订单，全部请求成功、全部成功出票。每轮 160 张票、库存余量 839，未出现重复出票或库存扣减差异。
- 修改后的 PASS 三轮调查任务数均为 0；REVIEW 三轮各完成 161 次调查（160 笔测量订单 + 1 笔预热）。
- 修改后共 483 次 AI 调用，测试服务记录的订单状态全部为 ISSUED。
- Java 测试总记录：92 项，91 项通过，1 项跳过；无失败或错误。跳过项是本机 Testcontainers Docker 适配问题，性能测试本身使用实际 MySQL。
- 验证了三类准入、出票失败时不提交调查消息、出票消息幂等、AI 等待时无事务且可并发锁订单、调查完成后下轮阻断、AI 不可用保留疑似、LOW 解疑以及画像更新保护。
- 实际服务补充验证：规则分 60 的订单先成功出票，AI 返回 HIGH、置信度 0.9、零调分后，Java 将画像判为 BLOCK（100 分）；本单仍为 ISSUED，下一次抢票返回 409，未创建预订请求。原始结果：results/post-issue-risk/live-block-check.json。

## 结论与限制

这组相同负载的测试显示，调整后抢票和出票吞吐均改善；消除了 AI 调查持有交易订单锁的路径，并减少了 PASS 的后台数据库工作。结果属于有限订单批次的对比，不是持续压力下的最大容量结论。

两组按先基线、后修改版本顺序执行，环境和 JVM 预热存在波动，部分基线轮次与本地构建重叠；中位数可降低单轮波动，但不能完全排除运行顺序的影响。真实 AI 延迟、不同风险比例和更长稳定负载需单独测量。画像来源时间仍使用现有订单时间精度，同秒结果没有新增严格序号；有效 BLOCK 的防降级与缓存版本保护不依赖该时间比较。
