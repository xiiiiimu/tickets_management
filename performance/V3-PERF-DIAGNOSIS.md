# V3 性能诊断（2026-10-31）

本轮只做测量和观测埋点。业务语义、风控、库存 Lua、支付、出票、Outbox 和一致性契约都没有改动。

## 0. 结论速览

1. **之前"V3 约 20 HELD/s、每单 CPU 比 V2 高 35%"主要是测量方法造成的，不是 V3 的真实表现。**
   - 原因一：预热只有 5 秒，JVM 还在做 JIT 编译。仅 JIT、GC 和 VM 自身就占了每单 21～31 ms 的 CPU。
   - 原因二：CPU 和成交数用的是两个不同的时间窗口。
   - 把预热延长到 60 秒，并用同一个窗口统计后：**V3 为 36～41 HELD/s，V2 为 31～33 HELD/s**；每单总 CPU V3 约 46.5 ms，V2 约 54.5 ms。
2. **现在的上限是这台 2 vCPU 机器的 CPU 已经用满**（应用、压测客户端、MySQL、Redis 加起来占 1.76～1.86 核）。按每单 46.5 ms 计算，上限约 43 HELD/s，实测 40。
3. CPU 的大头在 **MySQL 交互的固定开销**：
   - 每单约 10.9 个事务、103 条服务器端语句，其中**约一半**是 `SET autocommit`、事务隔离级别查询和设置、`COMMIT` 这类会话管理语句；
   - JVM 里 Worker 线程约 63% 的采样落在 MySQL 驱动（Connector/J 5.1.47）上，其中每条语句的超时任务 `CancelTask` 单独占约 30%。
4. Redis 不是瓶颈（每单约 2.5 ms CPU，0.1 核）。commit 的 fsync 在 active=4 时也不是瓶颈（HELD 事务 COMMIT 的 p50 为 3.0 ms）。全局协调锁的问题在 V3 中已经消失。

## 2. TPS 的统计口径（问题 1）

| 指标 | 业务节点 | 计数方式 | 时间分母 |
|---|---|---|---|
| HTTP QPS | 压测客户端发出的 POST | 窗口内发出的请求数 | 30 秒（固定 50/s） |
| 202 QPS | V3：Redis 受理 Lua 返回 ACCEPTED；V2：MySQL WAITING 已提交 | 窗口内 HTTP 202 的数量 | 30 秒 |
| Redis 预占 TPS | 库存 Lua 成功，**并且**它所在的事务已提交 | `lua_turn_finished=1` 的行数差 | 窗口长度 |
| 任务行插入 TPS | V3 开始处理时插入任务行（或超时终态行） | 本场次任务行数差 | 窗口长度 |
| MySQL INSERT 完成 TPS | HELD 事务里订单 INSERT 语句执行完毕（还没提交） | JDBC 探针：HELD 类事务中最后一条 INSERT 返回的次数 | 窗口长度 |
| **HELD TPS（COMMIT 确认后）** | HELD 事务的 `Connection.commit()` 已返回，即订单为 WAITING_PAYMENT，任务行为 RESERVED | ①窗口内任务行 RESERVED 数的差（提交后才可见）；②探针统计的 commit() 返回次数 | 窗口长度 |
| 出票 TPS | 支付后出票 | **本压测不支付、不出票，没有测量**，不能和 HELD TPS 混用 | — |

- **口径一致性**（预热组 V3 active=4 探针运行）：
  - HELD 事务里 INSERT 执行完毕 996 次，COMMIT 确认 996 次，没有回滚；
  - 窗口内 RESERVED 增加 999（差的 3 单在窗口边界）；
  - 合计 33.2～33.3/s，几种口径一致。
- 以前报告里的 `held_tps_steady`，是每秒采样一次 RESERVED 数，取测量窗口 20%～100% 之间的增长速率（只算已提交的）。它与上面的口径①偏差在 ±5% 以内。

- 把 active 从 4 提到 16，每一步都慢 3～4 倍，但吞吐只多 10%。这是 CPU 排队，不是锁。

**被拒请求（429）的额外开销**：对 4 次预热运行，用"Tomcat 线程 CPU = a·202 数 + b·429 数"做回归：

- 每个 202 约 2.4 ms Java CPU；

冷启动组被拒比例约 50%，这部分开销明显；预热组约 20%～27%。

## 5. CPU profiling，以及"高 35%"的来源（问题 4）

**方法**：
- 进程级：读 `/proc/<pid>/stat` 的 utime+stime 差值，分别取 Java、mysqld、redis-server；
- JVM 内按线程：Java 线程用 ThreadMXBean，非 Java 线程（JIT、GC）读 `/proc/<pid>/task/*/stat`；
- 热点：JFR 抽样，栈深 256；
- SQL：performance_schema 的 digest 统计；
- Redis：INFO commandstats。

**"V3 每单 CPU 高 35%"的计算方式（上一轮报告）**：只算 JVM 进程（应用加压测客户端），不含 MySQL 和 Redis；时间段是从开始发请求到排空为止；除以全部 RESERVED（含预热和排空阶段）。问题在于：

1. V2 排空阶段更长，两边时间窗口不同；
2. 没有包含 MySQL CPU（V2 每单的 MySQL CPU 反而更高）；
3. 预热只有 5 秒，JIT 编译、GC、VM 线程占每单 21～31 ms（冷启动组中这是 JVM 里最大的一块）。延长到 60 秒后，JIT（C1+C2）降到 2.5～3.7 ms，GC 1.7～2.7 ms。

**正确口径下的结论**：同一窗口、JIT 已预热时，V3 每单 CPU 比 V2 **低约 15%**（46.5 对 54.5 ms）。差别主要在 MySQL：V2 有协调锁、批量登记和领取相关的 SQL。

## 6. active_limit 扫描（问题 5）

**冷启动组**（预热 5 秒，**JIT 未稳定，绝对值偏低，只能用于横向比较**；每个配置 1 次，30 秒窗口）：

|---:|---:|---:|---:|---:|---:|---:|---:|
| 2 | 18.1 | 0.9% | 3.6 / 4.8 s | 83 ms | 0.07 s | 1.25+0.49+0.06 | 69 / 27 / 3.5 |
| 4 | 21.6 | 0% | 3.9 / 4.6 s | 125 ms | 0.37 s | 1.26+0.52+0.07 | 58 / 24 / 3.3 |
| 8 | 22.3 | 2.7% | 3.8 / 4.8 s | 250 ms | 1.6 s | 1.33+0.50+0.08 | 60 / 22 / 3.4 |
| 12 | 22.9 | 1.9% | 3.9 / 5.1 s | 384 ms | 6.4 s | 1.38+0.48+0.08 | 60 / 21 / 3.3 |
| 16 | 25.1 | 1.4% | 4.2 / 5.1 s | 482 ms | 8.2 s | 1.38+0.49+0.07 | 55 / 19 / 2.8 |
| V2 8 | 15.6 | **29.5%** | — | 175 ms | 96.7 s | 1.25+0.55+0.06 | 80 / 35 / 3.7 |
| V2 16 | 25.3 | 0% | — | 142 ms | 295 s | 1.18+0.63+0.06 | 47 / 25 / 2.3 |

**预热组**（预热 60 秒，各跑 2 次）：

| 配置 | HELD TPS | 超时 | Worker p50 |
|---|---:|---:|---:|
| V3 active=4 | 36.3 / 36.0 | 3 / 0 | 83 ms |
| V3 active=16 | 39.2 / 40.6 | 39 / 49 | 318 ms |
| V2 active=16 | 33.3 / 31.4 | 30 / 4 | 87 ms |

**结论**：
- active 从 4 提到 16，吞吐只多 8%～12%，Worker 延迟增加 3.8 倍，行锁等待增加 10 倍以上，并出现 3%～4% 的 202 后超时。
- active=4 时，约等于"4 个 Worker ÷ 每单平均 109 ms ≈ 37/s"，受并发数限制；active=16 时受 CPU 限制。
- 在这台机器上，active 取 4～8 是延迟、超时和吞吐之间的平衡点。
- 冷启动组的运行间波动约 ±20%（同样是 V3 active=16，上一轮 20.4、本轮 25.1）。单次结果不能用来下结论。

## 7. INSERT 执行完成 vs COMMIT 确认（问题 6）

JDBC 探针在每个物理事务上分别记录：最后一条 INSERT 返回的时间，以及 `Connection.commit()` 从调用到返回的时间。只有 commit() 正常返回才算提交成功，事务中间的状态 UPDATE 不算。

| 事务 | 语句执行 p50 | COMMIT p50 / p95 | 最后一条 INSERT 结束 → COMMIT 确认，p50 / p95 | 事务总时长 p50 |
|---|---:|---:|---:|---:|
| HELD（预热，active=4） | 15.1 ms | **3.0 / 9.2 ms** | **3.0 / 9.3 ms** | 23.5 ms |
| HELD（冷启动，active=16） | 79.9 ms | 16.6 / 71.4 ms | 16.9 / 71.4 ms | 139 ms |
| HELD（冷启动，V2 active=16） | 27.6 ms | 5.2 / 29.4 ms | 5.4 / — | 48.7 ms |
| T0（预热，active=4） | 5.6 ms | 2.7 / 8.5 ms | 3.8 / 11.5 ms | 9.2 ms |
| prepare（预热，active=4） | 8.4 ms | 2.7 / 8.0 ms | 2.7 / 8.1 ms | 14.5 ms |

窗口内计数：HELD 事务里 INSERT 执行完 996 次，COMMIT 确认 996 次，回滚 0。commit 本身不是瓶颈，并发高时变慢是因为 CPU 排队。

## 8. 瓶颈排序与证据

| 排名 | 瓶颈 | 证据 |
|---:|---|---|
| 1 | **单机 2 vCPU 的 CPU 已饱和**（压测客户端、应用、MySQL、Redis 共用） | 占用 1.76～1.86 核；2000 ms ÷ 46.5 ms ≈ 43/s，实测 40/s；active 增加只拉长延迟，吞吐基本不变 |
| 2 | **测量方式**：预热太短，CPU 和成交数窗口不一致 | 预热从 5 秒延长到 60 秒后，Java 每单 CPU 从 55～69 ms 降到 27 ms，HELD TPS 从约 20 升到 36～41 |
| 3 | **MySQL 服务器 CPU**：每单 17～19 ms，占总量约 37% | 每单 104 条语句，约一半是会话管理语句；每单 9.5～10.5 次 COMMIT |
| 4 | **MySQL 驱动的客户端开销** | Worker 线程 63% 的采样在驱动里，CancelTask 约 30%（事务超时 → Spring 给每条语句设查询超时 → 5.1 驱动为每条语句创建 CancelTask 并复制连接属性） |
| 5 | **每单事务数约 10.9** | 销售计划查询 2.5 个、流程中的续租 1 个，以及 current_owned、decided、T0、prepare、ordered-lua、HELD 各 1 个 |
| 6 | **并发过高** | active>8 时行锁等待集中在库存桶行和续租行，Worker 延迟增加 3～4 倍，202 后超时 3%～4% |
| 7 | **被拒请求的成本** | 每个 429 约 4.2 ms Java CPU，外加 1 个 MySQL 事务和 1 次 Lua；过载时占比上升 |
| 8 | **Stream 排队约 4 秒** | 容量把 5 秒窗口差不多排满，这是延迟和超时的主要来源，但不耗 CPU |

**已排除的方向**：
- Redis：每单约 2.5 ms CPU；
- 连接池：取连接等待 0.2 ms；
- active=4 时的 commit fsync：p50 3 ms；
- 全局协调锁：V3 的行锁等待 7～11 s，V2 是 352 s。

## 9. 优化项：预期收益、风险和最少修改范围

收益都是推断，需要逐项实测验证；建议按顺序做。

| 序号 | 优化 | 预期收益 | 风险 | 最少修改范围 |
|---:|---|---|---|---|
| 1 | **压测规范**：预热 60 秒以上，压测客户端放到单独的机器，每个配置至少跑 3 次 | 得到真实容量（本机已从约 20 修正到 36～41），后续结论才可信 | 无 | 只改压测脚本和流程 |
| 2 | **active_limit 设为 4～8**（这台机器） | 吞吐基本不变（−0%～−10%）；Worker p50 从 318 ms 降到 83 ms；202 后超时从约 3.7% 降到约 0% | 低 | 只改配置 |
| 3 | **JDBC 会话状态缓存**：`useLocalSessionState=true`、`useLocalTransactionState=true`、`cacheServerConfiguration=true`（`elideSetAutoCommits` 在 5.1 某些版本有缺陷，需要单独评估） | 每单服务器端语句减少约 10～25 条；MySQL 每单 CPU 降 15%～25%（约 3～4 ms），TPS 可能提升 5%～10% | 低到中：驱动会缓存会话状态，代码不能直接用 SQL 改会话变量（当前没有这种用法）。需要全量回归 | 只改 JDBC URL |
| 4 | **消除 CancelTask 开销**：升级到 Connector/J 8.x，或者改用 socketTimeout 加事务级超时，去掉逐语句的查询超时 | Java 每单减少约 3 ms（总量 6%～7%） | 中：驱动升级涉及时区和日期时间行为；去掉语句超时会改变超时处理方式，需要逐项确认 | pom 和 JDBC URL，或事务超时配置 |
| 5 | **缓存销售计划**（按场次、SKU、版本缓存很短时间），只用于 HTTP 入口和 Worker 读计划；prepare 和 HELD 事务里加锁校验 Armory 的步骤**保持不变** | 每单少约 2.5 个事务（约 12 条服务器端语句），被拒请求也更便宜 | 中：Armory 换版本时必须立即失效；版本的权威校验仍然在加锁的事务里 | V3Entry 加 1 处缓存，processAttempt 读计划改用缓存（或在 TicketSaleArmory 内部加只读缓存） |
| 6 | **V3 去掉流程中的那次续租事务**（心跳线程已经在续；prepare 的 `lockOwned` 会再核对 token） | 每单少 1 个事务，并消除续租行上的锁等待 | 中低：只能对 V3 生效，需要确认"续租失败就提前退出"的语义由 `lockOwned` 完整覆盖 | ReservationV2Service 中 1 处，加协议 4 条件 |
| 7 | **调整容量目标**：排队控制在 2～3 秒，并只用实测消化速率 | 端到端延迟从约 4 秒降到约 2 秒，202 后超时进一步减少 | 低到中：会多一些 429 | `V3StreamWorker.lastCap` |
| 8 | 429 异常不生成栈 | 每个 429 从约 4.2 ms 降到约 2.5 ms | 低 | AttemptAdmissionException 构造方法 |
| 9 | 合并事务（如 T0+decided、prepare+ordered-lua） | MySQL 收益最大（每单少 3～4 个事务） | 高：动到流程和围栏语义，按你的要求本轮不做 | — |

**建议优先的最少修改范围**：先做 1、2、3。全部是配置和测试流程，没有业务代码改动。实测确认后再做 4。5 和 6 各只改一两处，作为下一轮的候选。

## 10. 本轮的代码和工具变动

**生产代码（只加观测，不改控制流）**：
- 新增 `AttemptPath`（计时器 `attempt.path{phase,outcome}`）；
- `processAttempt` 里的 current_owned、plan_lookup、risk_classify、decided、heartbeat、prepare、reserve_and_held 包上计时，调用顺序和异常传播都不变；
- V3 计时项：受理 Lua、START Lua、Stream 排队、T0、process、超时终态记录、结算、端到端。

**回归**：单元测试 371/371；V3 端到端测试中的正常流程、崩溃接管、超时围栏都通过。

**压测工具**（`performance/results/v3-diag-20261031/`，不属于生产代码）：
- `DiagSnapshot`：窗口起止快照，覆盖进程 CPU 和上下文切换、JVM 线程和原生线程 CPU、GC、MySQL 状态和 digest、Redis commandstats 和 CPU；

- 压测脚本：输出分位数，排空时把 V3 的 Stream 一起等完。

**原始数据**：每个运行的 `steady.json`（含 `diag`、`jdbc_probe`、`timer_percentiles`），以及 JFR 热点汇总。
