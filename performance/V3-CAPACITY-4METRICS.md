# V3 容量：四项指标实测（2026-10-31）

## 测试条件（读数前先看）

- **硬件**：1 台 2 vCPU（Xeon 2.8 GHz）、7 GB 内存的云主机。应用 JVM、压测工具 wrk、MySQL 8.0.46、Redis 7.0.15 全在这台机器上，绝对值只代表这台机器。
- **V3 配置**：active_limit=16，workers=16，连接池 30，Redis 到达顺序模式开启，风控快审开启，30% 用户走 REVIEW。
- **压测工具**：wrk 4.1 闭环压测，独立进程，2 个线程。
  - **每个请求的 requestId 都不同**（运行编号 + 线程 + 序号）。
  - 6 万个用户轮流使用，每个用户有独立 token、IP 和风险画像。
  - 用户会重复出现：同一用户上一个请求还在处理时，新请求会被当作别名或触发单用户上限。
- **预热**：正式测量前，先在另一个大库存场次上用 wrk 跑 60 秒（32 个连接），让 JIT 编译完成。
- **计数口径**：服务端每秒采样一次。
  - HTTP 处理数：取自 `http.server.requests`；
  - Redis 受理数：受理 Lua 返回 ACCEPTED 的次数，即成功 XADD 的新 requestId；
  - HELD：MySQL 中 RESERVED 的行数，提交之后才可见。
  - 稳态速率都去掉了每阶段开头 2 秒和结尾 1 秒。
- **样本**：每个场景只跑了 1 次。按前一轮的经验，单次结果大约有 ±10% 的波动。

## 1. HTTP 最大 QPS（含 429）

| wrk 连接数 | 服务端 HTTP QPS | wrk QPS | 202 / 429 | 延迟 p50 / p90 / p99 | Redis 受理 TPS | HELD TPS | 核数（Java/MySQL/Redis） |
|---:|---:|---:|---|---|---:|---:|---|
| 8 | 320.6 | 313.6 | 932 / 8500 | 24 / 60 / 152 ms | 26.7 | 25.7 | 1.1 / 0.6 / 0.1 |
| 32 | 469.3 | 467.7 | 625 / 13432 | 63 / 116 / 189 ms | 16.4 | 12.6 | 1.1 / 0.6 / 0.2 |
| 128 | 518.8 | 522.3 | 487 / 15223 | 232 / 376 / 560 ms | 10.6 | 7.6 | 1.2 / 0.5 / 0.2 |
| **256** | **583.4** | **585.0** | 449 / 17144 | 427 / 622 / 903 ms | 8.5 | **5.4** | 1.2 / 0.5 / 0.1 |

- **这台机器上 HTTP 最大 QPS 约 585 次/秒**（256 个连接）。
- 所有阶段都没有连接错误、读写错误或超时，响应只有 202 和 429。
- 继续加连接只会让延迟变长，QPS 基本到顶。
- **注意**：HTTP 压力越大，HELD 越低（25.7 → 5.4）。原因是被拒请求也要走完整的 HTTP 处理链：鉴权读 Redis、参数校验、fingerprint、销售计划查询（一个 MySQL 事务）、受理 Lua、异常处理。这些开销和 Worker 抢同一块 CPU。

## 2. Redis 受理成功 TPS（每秒成功写入 Stream 的不重复请求）

| 场景 | 平均 | 峰值（1 秒） |
|---|---:|---:|
| 开售瞬间（5000 张票，洪峰） | — | **169/s**（受理容量在 1 秒内被填满） |
| 开售瞬间（约 160/s 的中等需求） | — | 116/s |
| 售卖期间，中等需求 | **43.5/s** | — |
| 售卖期间，洪峰（约 517/s） | 15.6/s | — |
| HTTP 测试，8～256 连接 | 26.7 → 8.5/s | 44 → 23/s |

受理 TPS 的上限不在 Redis，而在受理容量：容量按"处理速度 × 约 4 秒"放行，排队满了就返回 429。所以持续受理 TPS 约等于 HELD TPS 加上排队超时的数量。

作为参照，前一轮用独立微基准单测受理 Lua，约 1.5～2.2 万次/秒，远高于 HTTP 链路能送到它的量。

## 3. MySQL HELD TPS（每秒提交成功的有效锁单）

| 场景 | 开售到售罄的平均值 | 稳态（第 10 秒到售罄） | 峰值（1 秒） |
|---|---:|---:|---:|
| **中等需求（约 162/s）** | **40.6/s** | **41.1/s** | 58/s |
| 洪峰（约 517/s） | 11.5/s | 11.6/s | 20/s |
| 前一轮稳态测试（50/s 开放模型，预热 60 秒） | 36～41/s | — | — |

## 4. 5000 张票的清空时间（开售 → 5000 张都成为已提交的 HELD 订单）

| 需求 | **清空时间** | 第一单 HELD | 202 后排队超时 | 售罄后受理的请求 | 不变量 |
|---|---:|---:|---:|---:|---|
| 约 162/s（20 连接，每个连接间隔 100 ms） | **123.3 s** | 0.42 s | 93 | 268（处理结果为 SOLD_OUT） | 5000 单；MySQL 库存 0、Redis 库存 0；5000 个不同买家；没有超过限购的；没有残留的 REQUESTED |
| 约 517/s（64 连接，不间隔） | **435.5 s** | 1.34 s | **1544**（约 23%） | 92 | 同上，全部满足 |

- **清空时间的计时**：从销售开始时间（sale_start_time）起，到 MySQL 中 RESERVED 达到 5000 为止。每 200 ms 轮询一次，误差不超过 200 ms。
- 两次都没有超卖或重复订单，排空后也没有遗留的处理中任务。

## 结论

1. **这台单机上 V3 能达到约 41 HELD/s，5000 张票约 2 分钟卖完。前提是到达应用的请求量在每秒一两百以内。**
2. **请求真正形成洪峰时（约 500/s），被拒请求本身就会吃掉 CPU，HELD 降到约 11.5/s，清空时间变成 7 分多钟，还有约 23% 拿到 202 的请求最终排队超时。** 这是当前最大的容量风险，比数据库事务数更紧迫。
3. **HTTP 最大 QPS 约 585**，这时延迟 p50 约 0.43 秒，而且基本没有出票能力。这个数字反映的是"能拒得多快"，不是"能卖得多快"。

## 下一步建议（需要你确认后再做）

| 序号 | 建议 | 说明 |
|---:|---|---|
| 1 | **在入口最前面挡住过载**：入口全局令牌桶（`ticketing.ingress.post-rate`，目前测试里设为 100000）设到约 200/s 左右，或者在网关或 Nginx 限流 | 只改配置，被拒请求不再进入完整处理链 |
| 2 | 受理容量已满时尽量少做事 | 例如先查一次 Redis 里的容量标志、在入口缓存销售计划、429 异常不生成堆栈。需要少量代码 |
| 3 | 把压测工具和数据库放到独立机器上再测 | 否则 wrk 和被拒请求的开销会一直算在这台机器上 |
