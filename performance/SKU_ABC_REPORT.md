# 同 SKU 16 库存桶：A/B/C 架构实验

日期：2026-10-08。C 是一个 SKU 的真实桶库存，不是把同一商品改成多个 SKU。

## 结果

| 组 | 模型 | QPS 中位数 | Avg ms | P95 ms | P99 ms |
|---|---|---:|---:|---:|---:|
| A | 1 SKU / 1 库存行 | 5.33 | 5383.33 | 7966.55 | 9211.14 |
| B | 16 SKU / 每 SKU 1 库存行 | 9.41 | 3316.80 | 5262.06 | 6465.12 |
| C | 1 SKU / 16 库存桶 | 9.52 | 3008.09 | 4580.60 | 5698.11 |

C 相对 A 的 QPS 中位数变化为 +78.6%，相对本轮 B 为 +1.2%。三轮样本仅支持本次负载下的比较，不能证明 C 普遍优于 B，也不能推断最大持续容量。历史 B 的 8.02 QPS 未混入本表。

## UPDATE 相关阶段、行锁与连接池

库存阶段 A/B 为原单行 UPDATE；C 包含桶 UPDATE + 同事务写入分配记录，其成本完整计入。该阶段 JDBC 耗时不是纯行锁等待。行锁列为隔离数据库 Innodb_row_lock_time 的三轮增量总和，覆盖请求与后台出票完成，包含周期性维护及其他事务的行锁。

| 组 | 库存阶段 Avg ms | P95 ms | 累计行锁等待 ms | 等待次数 | active 平均/峰值 | pending 平均/峰值 |
|---|---:|---:|---:|---:|---|---|
| A | 1336.71 | 2012.96 | 643759 | 480 | 9.41/10 | 18.89/28 |
| B | 9.60 | 18.46 | 2914 | 14 | 7.34/10 | 1.78/16 |
| C | 18.86 | 100.45 | 6209 | 41 | 6.97/10 | 1.33/16 |

连接池来自负载期间每 200ms 的 Hikari MXBean 直接采样，均值与峰值按客户端请求窗口筛选；负载期间不抓全量 Prometheus，以免触发额外的数据库统计查询。

## 配置与公平性

- 同一当前版本、同一 Java 8 进程、MySQL 8 / Redis 7 / RocketMQ 4.9.7；32 clients、160 requests，每单 1 张、160 个不同用户和请求 ID。
- 所有组均存在相同的 16 个 SKU，每个初始库存 1000；A/C 的 160 笔测量均使用 SKU-001，B 每 SKU 10 笔。
- C 的 SKU-001 总量仍是 1000，拆成 16 条库存行：桶 0–7 各 63，桶 8–15 各 62；没有把可卖库存扩大 16 倍。
- JVM -Xms128m -Xmx384m -XX:+UseSerialGC；Hikari max=10；保持原线程池、支付、出票、工作流、事务范围及后台任务。风控固定 PASS，无 AI 调查。
- B 与 C 分别充分预热，至少四批 160 请求，最后两批 QPS/Avg 相邻变化均小于 15%。预热库存用 10000，正式测量统一恢复 1000。
- B 预热 5 批 / 800 请求，最后两批 QPS：8.85、9.11。
- C 预热 4 批 / 640 请求，最后两批 QPS：8.55、8.27。
- 顺序 A1 → B1 → C1 → B2 → C2 → A2 → C3 → A3 → B3；测量期间没有构建或重启服务。每轮全部出票后才清理数据。
- 每轮测量前，对同样的 16 个 SKU 各做一笔独立用户预热并等出票完成；这 16 笔不计入 160 测量请求。

## C 实现及协调成本

- 可选开关 ticketing.inventory.bucket-count，默认 1。实验开启 16；只有在数据库中初始化了 16 个完整桶的 SKU 才走分桶路径，A/B 仍用原库存行。
- 同 SKU 使用 16 个 Redis 库存键、16 条 MySQL 桶库存行。Redis Lua 按请求 ID 哈希选首选桶，空桶时最多探测 16 桶，同时维护 SKU 级用户限购和预占幂等标记。
- Lua 返回实际选中的桶；MySQL 在原抢票事务内做桶库存条件 UPDATE、写 reservation/request→bucket 分配记录及订单，事务失败则桶库存与分配记录一同回滚。
- 扣减条件保留库存充足与当前售卖状态、销售时间校验。配额、落单和工作流仍在原事务里；没有通过提前提交或删减交易步骤让 C 变快。
- C 不在每笔预订中扣减原 SKU 行；权威总余量为桶 SUM。Repository 读取该逻辑值，原 SKU remaining_stock 由正常 30 秒后台刷新做聚合投影。C 三轮原 SKU version 均为 0、桶 version 总和均为 161，校验了没有逐单走原单行扣减。
- 回补按持久化分配记录恢复 MySQL 原桶，按 Redis 预占标记的 stockKey 恢复 Redis 原桶；重复回补不会重复加库存。
- Redis 保持同一节点与同一 SKU hash slot，保留 Lua 原子性；本实验没有验证 Redis 多节点扩展。C 额外包含桶就绪检查、桶求和查询和分配记录 INSERT 的实际成本。

## 超卖、重放与失败补偿

- 真实服务耗尽测试：同 SKU 总库存 16、每桶 1，预热占 1；160 请求中 15 成功、145 返回 409。最终 16 张全部出票，桶/Redis/原 SKU 余量都为 0，没有负库存或超卖。
- 重放成功请求返回原订单，未增加扣减或出票。
- 独立故障注入：Redis 放行后故意令 SQL 限购失败。原事务回滚，MySQL 桶仍余 999、没有新增分配或订单，Redis 暂时 HELD 余 998。
- 将失败 intent 的时间设为过期，正常调度恢复到原 Redis 桶，余量回到 999；失败 intent 状态 FAILED、标记 RELEASED。再执行相同释放 Lua 返回 0，余量仍为 999。此测试验证最终补偿，不是 Redis/MySQL 跨库强原子提交。
- Java 回归记录：96 项，95 项通过，1 项因本机 Testcontainers 适配跳过。新增 4 项覆盖并发防超卖、回滚、重复回补/聚合投影与默认关闭。

## 范围与产物

这是默认关闭的静态 16 桶实验实现。开启前需应用 V103 表结构，并在首次配置和放量前初始化新 SKU 的完整桶；不支持把已有普通预占的 SKU 在线切换，也未验证在线扩缩桶或大单跨桶拆分。每个订单由一个桶供给，本实验只验证每单 1 张。
同一机器上仍可能有资源和 JVM 波动；桶哈希分布、销售状态校验、原事务持锁范围、Redis 协调与周期投影均可影响性能。C 接近本轮 B 不构成达到历史 8.02 或任意容量目标的保证。

- 脚本：performance/compare_inventory_buckets.py；故障补偿：performance/check_inventory_bucket_compensation.py。
- 原始逐请求计时、200ms 池采样、三轮每桶数据、日志与构建包：performance/results/sku-abc/。
- 应用参数：--ticketing.inventory.bucket-count=16 --ticketing.perf-log.enabled=true --ticketing.perf-log.pool-interval-ms=200，时区 UTC；其他环境沿用本次隔离 credit-risk-ab 服务。
