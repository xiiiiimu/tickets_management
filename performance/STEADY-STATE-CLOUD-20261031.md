# 稳态压测（云端容器，2026-10-31）

**环境限制（读数前必须先看）**：2 个 vCPU、7GB 内存的云端 Linux 容器，**应用、压测客户端、MySQL 8.0.46、Redis 7.0 全挤在这一台上**。所以本报告的绝对数字反映的是"2 核机器的极限"，不是系统容量。可信的是：同一台机器上新旧配置的相对差异，以及"每张票消耗多少 CPU"。

## 方法

- 工具：`results/steady-state-cloud-20261031/SteadyStateExperimentIT.java`。它启动真实的 Spring Boot 服务（随机端口），**热路径上没有任何 Mockito spy**，压测客户端通过 HTTP 调用 `/api/tickets/reservations`。
- 开放模型：按固定到达率发请求，不等上一个返回。先预热 5 秒，再测 30 秒，然后最多等 60 秒让剩余任务处理完。
- 每个请求都是独立的用户、token、风险画像（30% REVIEW），客户端 IP 也各不相同（通过受信任的本地代理设置 X-Forwarded-For），不会人为触发按 IP、按用户的风控限流。
- 库存设为每个 SKU 2 万张，整个过程不会卖完。
- 结束时检查不变量：MySQL 库存 = Redis 库存 = 初始库存 − 订单数；订单数 = RESERVED 数；没有残留的 WAITING/PROCESSING 任务。**所有运行都满足**。
- "HELD TPS（稳态）"取测量窗口 20%～100% 这段时间里 RESERVED 数的增长速率。

## 结果

| 配置 | 发送速率 | 202 速率 | **HELD TPS** | 每张票的 JVM CPU | 响应构成 |
|---|---:|---:|---:|---:|---|
| 原配置（新开关全关，并发上限 4） | 50/s | 25/s | **15.3** | 80 ms | 202 一半，429 一半（DB_BUSY 和等待预算） |
| 原配置 | 100/s | 18/s | **9.6** | 130 ms | 82% 是 429，过载后吞吐反而下降 |
| 新配置（Redis 到达顺序 + 闸门 + 批量登记，并发上限 16） | 50/s | 见下 | **25.0** | 38 ms | 全部 503（见下） |
| 新配置 | 100/s | 见下 | **22.7** | 33 ms | 同上 |
| 新配置，4 个 SKU | 100/s | 见下 | **22.8** | 33 ms | 同上 |

1. **在相同的 2 核机器上，新配置的成交速率提高 1.6～2.4 倍，每张票的 CPU 消耗降到 40%～50%。** 原配置在 100/s 时出现过载退化（成交从 15 掉到 10），新配置没有。
2. **单 SKU 和 4 个 SKU 结果一样（22.7 对 22.8）**，说明 SKU 通道已经不是瓶颈，瓶颈在机器本身和全局协调。
3. **新配置在这台机器上 HTTP 全是 503，但请求实际上都登记成功并完成了**：批量登记的积压超过了 HTTP 的等待时间（默认 1 秒），调用方等不及就返回 503 `VALIDATION_UNAVAILABLE`，按照约定，客户端需要用 requestId 再查询。这个语义是对的，但体验不好。
   - 为此加了一个可选开关 `batch-register-backlog-guard`（默认关闭）：积压预计来不及提交时，直接返回 429。实测打开后成交速率降到 14～18/s（结果见 `*-backlog-guard.json`），所以先默认关闭。
   - 真正的解决办法是让登记更快，见下面的瓶颈分析。

## 瓶颈（压测过程中的计时器和 JFR 采样）

- **CPU 饱和**：JVM 用掉 1.2～1.5 个核，MySQL 只能用剩下的部分。
- **全局协调行（tb_reservation_dispatch id=1）仍然是热点**：负载下，claim 事务体平均约 400ms，批量登记事务体平均约 540ms（每批 16 条）。两者都在排同一把行锁。这是下一步要优化的地方。
- **MySQL 驱动的额外开销**：mysql-connector-java 5.1.47 在每条带查询超时的 SQL 上，都会复制一次连接属性（`StatementImpl$CancelTask`），这部分约占 CPU 采样的 13%。超时来自各个 TransactionTemplate 设置的事务超时。可以考虑升级驱动（例如 8.0.x），但需要单独回归测试。

## 对 170 TPS 的粗略换算（不是实测）

新配置每张票大约消耗 33～38ms 的 JVM CPU（含压测客户端的开销）。按这个算，170 TPS 光应用就需要约 6 个核，还要另外给 MySQL 和 Redis 留出资源，同时要先解决协调行的争用。所以建议的验收环境是：应用一台（8 核以上）、MySQL + Redis 一台（SSD 云盘）、压测客户端单独一台。
