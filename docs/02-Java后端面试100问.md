# Java 后端面试 100 问与回答

## 使用方式

每题包含直接回答与项目细节，适合先口述核心结论，再根据追问展开。实现事实以当前源码为依据；尚未实现的方案明确标为讨论。不要把本册中的排障思路当作自己真实经历，也不要将未执行的测试结果写进简历。

本文依据 2026年9月17日工作区源码、DDL、配置与现有测试源码整理。它是源码说明，不是本次真实环境验收报告；未重跑的测试、容器状态、吞吐量和模型效果均不作为已验证结论。

## 1. 简单介绍一下这个项目的后端职责边界

ticket-risk-platform 是唯一交易与最终风险决策服务：库存预占、订单状态机、Outbox、自动支付确认、规则引擎都在 Java。risk-agent 只提供 REVIEW 调查建议，不写交易库。前端只负责发起与轮询。

项目细节与追问：介绍时先交代单 SKU 交易聚合，再说同步受理和异步履约。把业务目标、数据权威和异步边界讲出来，比罗列框架更能证明理解。

## 2. 为什么保留 Java 8 和 Spring Boot 2.3

当前工程继承这套运行时，重构重点是显式事务与职责拆分。可以解释兼容和迁移成本，但不能把历史版本说成技术上永远更优。本仓库没有给出最初选型会议记录；这里是根据现状分析取舍。

项目细节与追问：源码锚点是 pom.xml。Spring Data Redis 与 Lettuce 有单独覆盖版本，不能假设全部依赖都由 Boot BOM 自动协调；版本升级需要编译、兼容与回归证据。

## 3. 核心交易为什么使用 JDBC Repository

显式 SQL 让库存条件扣减、订单 status/version 更新和 Outbox 租约易于审查。Repository 隔离 SQL 与编排，同时保留类型映射。JPA、MyBatis 同样能写条件 SQL，并非天然不能做并发；当前选择主要减少额外迁移和隐式行为。

项目细节与追问：举例对比库存 UPDATE 的 remaining_stock>=quantity 与订单 UPDATE 的 status/version 条件，说明 Repository 不是把 SQL 隐藏起来，而是让业务编排更清楚。

## 4. 什么是 Typed Model？你们做到什么程度

对有整行读取的对象建 `TicketOrder`/`ReservationIntent`/`TicketSku`，服务层用 getter。Reservation/UserPurchase 无整行读需求，保留原子 Repository API，不硬造空 POJO。不是完整 DDD。

项目细节与追问：类型对象减少字段名拼错和 Number 强转，但当前订单列表等接口仍返回 Map。不能说所有 API 已统一 camelCase，也不能说模型已经不可变。

## 5. 抢票接口的同步路径做了哪些事

鉴权绑定 userId、取 IP、滑动窗口限频、黑名单、读取已有 RiskProfile、轻量 fast 规则；通过后落 ReservationIntent、Lua 预占、MySQL 事务扣库存/限购并写 reservation/**WAITING_PAYMENT** order/`RISK_CHECK` Outbox，afterCommit 自动支付。深度分析在 MQ 消费侧只更新画像。

项目细节与追问：库存 configure 与意图创建都有数据库工作。所以“没有 Agent”可以由调用链证明，“毫秒响应”只能由真实测量证明。

## 6. fast() 和 evaluate() 有什么区别

fast：当前请求准入（限频/黑名单/RiskProfile/轻量规则），失败直接拒，不等待 Agent。evaluate：交易后深度打分，仅 REVIEW 调 Agent，落 `tb_risk_decision` 并 upsert `tb_risk_profile`，**不改当前订单状态**。

项目细节与追问：已 COMPLETED 请求优先走幂等返回，不会照搬所有新请求的风控步骤。

## 7. 为什么深度风控放异步而不是同步抢票里

抢票要低延迟；更关键的是业务语义——深度结果只服务后续请求画像，不应阻塞已通过准入的当前履约。Outbox 保证「单已创建必有分析消息」，消费幂等保证画像副作用一次。

项目细节与追问：消费内部 Agent HTTP 仍可同步占用 risk 池，但不回头改订单、不阻止自动支付。

## 8. 解释 ReservationIntent 与 REQUIRES_NEW

意图在 Redis 前先落库，传播 REQUIRES_NEW+READ_COMMITTED，使「请求已接受」不因后续主事务回滚消失，补偿任务可扫 REQUESTED 孤儿并释放。

项目细节与追问：reservationId 与 orderId 在意图创建时预分配。即使主事务失败，恢复任务仍知道应释放哪个 Redis reservation，而不必猜测请求是否执行到 Lua。

## 9. Redis Lua 预占解决什么

把开售窗、限购、库存、用户计数、指纹幂等、HELD 标记放进同一原子脚本，避免多往返竞态。SKU 键用 hash tag 保证同槽。

项目细节与追问：Lua 返回 1 表示新预占，2 表示同指纹重放；负数代表不同拒绝原因。原子性仅覆盖同次脚本中的 Redis 操作，不覆盖随后 MySQL 提交。

## 10. 为什么还要 MySQL 条件更新

Redis 不是最终账本。MySQL remaining_stock 与 tb_user_purchase 的条件更新是持久化防线，防止缓存丢失或逻辑漏洞导致超卖。

项目细节与追问：数据库检查与缓存闸门相互补充。要验收的不只是“成功数小于库存”，还包括剩余库存非负、订单数量匹配、释放后的总量守恒。

## 11. fingerprint 和 requestId 分别解决什么

requestId 标识一次受理，fingerprint 将用户、场次、SKU、数量、设备绑定到这个请求号，摘要不含 IP。相同号不同参数拒绝；换号属于新请求，仍可在限购内成功。MD5 在这里用于参数一致性，不是防伪签名。

项目细节与追问：面试追问“同 requestId 并发 20 次”时，应同时核对意图一行、reservation 一行、order 一行和 RISK_CHECK Outbox 一行，而不是只看 HTTP 成功次数。

## 12. HELD / RELEASED 如何防双释放

release Lua 只在 HELD 时回补库存并标 RELEASED；非 HELD 返回无操作。重复 RELEASE 消息不会加两次库存。

项目细节与追问：业务层先用 MySQL reservation HELD 条件更新守门；Redis Lua 再守一次。一个系统内的幂等不能替代另一个系统的幂等。

## 13. Redis 丢键了能不能按 total_stock 回填

当前策略：有交易历史的 SKU 不盲目回填，停止新预占等待维护。完整停写重建工具尚未提供，面试要诚实。

项目细节与追问：源码以 remaining_stock==total_stock 且无意图记录约束初始化。缺键时拒绝售卖可能牺牲可用性，但比凭空恢复总库存更易保持账本正确。

## 14. 订单状态机有哪些主状态

CREATED 可直达 WAITING_PAYMENT（新主链落单即此态）；历史仍保留 RISK_CHECKING/REVIEW/BLOCKED 边。WAITING_PAYMENT→PAYING→PAID→ISSUED；以及超时、取消、退款态。深度 BLOCK **不会**把已成功订单改回 RISK_BLOCKED。

项目细节与追问：取消并非任意状态都允许，RISK_REVIEW 也没有直接 CANCELLED 边。应背合法迁移表而不是把所有终态当成可自由跳转的字符串。

## 15. 状态迁移如何并发安全

OrderStateMachine 校验合法边，Repository tryTransition 带 id+from+version 条件更新，失败即并发冲突。

项目细节与追问：内存对象在条件更新成功后同步递增 version，便于同事务连续 PAYING→PAID。旧对象继续写会被 CAS 拦住，而非静默覆盖新状态。

## 16. 为什么保留 WAITING_PAYMENT 和 PAYING

复用超时/取消边；支付确认与后置画像分析拆开：落单即 WAITING_PAYMENT 并自动支付，深度结果只写 RiskProfile。

项目细节与追问：中间态也增加恢复责任。不能仅保留状态名就声称支付重试完整，应核对谁触发下一步、失败后由谁重新执行。

## 17. Outbox 模式解决什么问题

避免业务成功但消息没发出或消息发出但业务回滚。消息行与业务同事务提交，Publisher 异步投递。

项目细节与追问：MANDATORY 强制消息登记处于已有事务，Publisher 再独立发送。这里解决单库提交与发送的双写窗口，不保证 Broker 和数据库原子提交。

## 18. Outbox Publisher 如何避免多实例同时领取

读取到期候选后，用条件 UPDATE 将状态改为 SENDING 并写 lease_token 与 60 秒租约。只有领取成功的实例发送；后续标 SENT 或 RETRY 都比较令牌。多实例可以读到同一候选，但不能同时拥有同一有效租约。

项目细节与追问：旧工作者发送慢时可能跨越租约，令牌比较阻止其覆盖新拥有者的状态；但它已经发出的网络消息仍可能重复，所以消费者幂等必须存在。

## 19. 消息已发送但标记 SENT 前崩溃怎么办

租约到期后消息可能重发，这是至少一次投递的必然窗口。不能用“发前标成功”消除重复，否则会丢消息。消费者依靠消费记录、订单状态和业务唯一键，把重复传输收束为一次有效副作用。

项目细节与追问：SENT 和 DONE 分别表示发送确认与消费本地完成。排障要分别查看，不能看到 Outbox SENT 就断言订单已出票。

## 20. Outbox 重试与补偿的具体规则是什么

Publisher 每批最多 50 行，发送等待 3 秒，失败退避，默认 12 次后 FAILED。补偿会重排五分钟未 DONE 的 SENT，并重试一小时以上的 FAILED。当前指数表达式最高退避 256 秒，而不是直接套用外层 300 秒上限。

项目细节与追问：FAILED 不是永久终态，补偿会重置老失败行。没有实际生产监控证据时，不宣称这些重试已满足某个 SLA。

## 21. 消费幂等为什么需要本地事务

消费记录与订单、支付后续消息等数据库副作用必须同事务提交。先单独保存 DONE 会出现业务未执行却不再重试；后单独保存又可能重复执行。Redis RELEASE 是外部副作用，另用 Lua HELD 状态保护重入。

项目细节与追问：原子提交保护的是同一数据源。若以后消费者调用第三方扣款，本地事务不能回滚该外部动作，必须另设计渠道幂等与对账。

## 22. 为什么还有 business_key 约束

message_key 是当前消息标识，business_key 表达消费业务身份。两者与 consumer_group 分别形成约束，使不同消费者可独立处理。当前两者都围绕 type:orderId，不能据此宣称已覆盖任意未来消息拆分与版本兼容。

项目细节与追问：消息正文的 messageKey 被校验为 type:orderId。即使 RocketMQ 生成不同物理消息 ID，当前同一业务事件仍能被去重。

## 23. 自动支付从哪里触发

RISK_CHECK 消费最终 PASS 时转 WAITING_PAYMENT 并注册 afterCommit；人工审核 APPROVE 则在审核事务返回后由 AdminController 调 attempt。两条路径共享 AutoPaymentExecutor 和固定支付幂等键，没有第三方支付回调。

项目细节与追问：主链自动确认不再次执行 Wallet 的 PAYMENT 风控，也不做余额检查。不要拿兼容支付的分支当作主链必经步骤。

## 24. afterCommit 是否代表异步线程执行

不是。当前回调在事务提交后的同一线程调用 attempt，没有提交到支付线程池。它提供的是提交顺序保证：外层回滚不支付。独立支付事务由另一个 Spring Bean 上的 REQUIRES_NEW 提供。

项目细节与追问：afterCommit 异常可让调用者看到失败，而外层事务已提交。因此接口错误与数据库回滚不能画等号，要查询订单和消费事实。

## 25. REQUIRES_NEW 在 AutoPaymentExecutor 的意义

支付确认使用独立事务：锁单、Payment SUCCESS、PAYING→PAID、append ISSUE 一起提交；也满足 Outbox MANDATORY 需要活跃事务。

项目细节与追问：独立 Bean 避免自调用绕过事务代理。内部状态和 ISSUE 一起提交，才能保证“支付确认成功但无出票消息”不成为正常提交结果。

## 26. 自动支付幂等键有哪些

payment_request_id=`AUTO_PAY:<orderNo>` UNIQUE；成功态 success_key=`PAYMENT:<orderId>` UNIQUE；订单行锁+状态机。

项目细节与追问：固定请求键是自动路径的请求幂等，success_key 是跨不同请求的业务成功幂等。锁单负责串行化组合检查，唯一键仍是最终防线。

## 27. 重放已有 SUCCESS 为什么不再 ISSUE

支付事实已存在则出票消息应已挂过；再 append 增加无意义投递。消费端仍有幂等兜底。

项目细节与追问：这依赖支付记录与 ISSUE 同事务创建。若运维手工破坏 Outbox，重复支付并不是专门修复损坏数据的工具。

## 28. Demo 主链为什么不扣 Wallet

叙事是「fast 准入通过即履约确认」，深度画像后置；不接三方也不模拟余额不足。Wallet 保留兼容 /pay 与退款，同样只做 fast 准入，不是正常抢票必经。

项目细节与追问：面试可以展示工程闭环，但必须说清 SUCCESS 是 Demo 本地确认。若使用“扣款成功”“到账”等词，会误导对真实资金能力的判断。

## 29. 手动 /pay 还在吗？会不会双付

接口仍在。若 AUTO_PAY 已成功，再次 /pay 不得再产生成功支付；靠 payment 唯一约束与订单状态校验。

项目细节与追问：已经 PAID 或 ISSUED 的订单不满足 Wallet 支付状态。自动支付与钱包支付共享成功业务键，数据库事务避免一次冲突只留下余额扣减。

## 30. success_key 和 payment_request_id 为何都要

前者防同一订单被不同 request 多次成功；后者防同一请求重试插入多行。两者维度不同。

项目细节与追问：失败支付的 success_key 可空，因此可记录不同失败尝试；payment_request_id 仍唯一。相同失败请求重放不能重新扣款，应使用新的业务尝试键。

## 31. 当前退款路径有什么必须说清的限制

WalletService.refund 给钱包加订单金额、写退款交易与流水、删票并释放库存。主链 AUTO_PAY 从未扣钱包，而退款未区分原支付渠道，已有钱包可能获得非对应原扣款的加款；没有钱包则失败。因此它不能被包装成真实资金闭环。

项目细节与追问：这属于静态源码发现的语义风险，本次未运行自动支付后退款实验。面试应如实说“待验收”，不能编造已修复结果。

## 32. 策略注册后的规则引擎如何组织

引擎遍历启用规则，Registry 按 supports 找唯一策略，当前由 GenericThresholdRuleEvaluator 处理特征阈值及附加条件。多策略同时支持会报错，无策略则跳过，重复策略类在构造时拒绝。DECISION_POLICY 提供最终阈值与调分上限。

项目细节与追问：扩展策略需要在 Spring 中提供实现并保证 supports 不重叠；新增数据库规则行不等于新增一种任意可执行算法。

## 33. 黑名单存在哪里

Redis key `risk:blacklist:{user|device|ip}:{value}`，Admin 设置 TTL；evaluate/fast 都会检查。

项目细节与追问：当前黑名单维度是 user/device/ip，管理端限制 TTL 最大 30 天。黑名单状态属于 Redis 实时策略，不是数据库中的完整处罚历史。

## 34. 为何 PASS/BLOCK 不调 Agent

明确决策不应等待 LLM；降成本与时延。只有 preliminary=REVIEW 才 HTTP 调查。

项目细节与追问：可以直接指向 preliminary == REVIEW 的条件表达式作为证据。不要继续沿用旧文档“所有 evaluate 都调用 Python”的描述。

## 35. Agent 不可用时 Java 怎么继续

RiskAgentClient 对缺密钥、HTTP 异常、空结果或不可用响应统一返回 aiAvailable=false、scoreAdjustment=0。RiskDecisionService 继续按规则分和黑名单决定。REVIEW 仍进入审核，降级不是所有用户自动 PASS。

项目细节与追问：模型不可用和服务权限错误在 Python HTTP 层不同，但 Java 客户端都可安全收敛为 unavailable。业务决定仍需要规则配置与 Redis 特征可用。

## 36. 为什么 Agent 不能把 REVIEW 降成 PASS

Java 只增加 max(0,min(cap,adjustment))，规则分不会下降。在有效阈值下，初判 REVIEW 最终仍是 REVIEW 或升为 BLOCK；Python 返回负分也归零。最终结果由 Java 的 decide 算出，不读取自然语言当命令。

项目细节与追问：risk_decision.score 保存调整后分数，而不是分别保存 baseScore 和 finalScore。回溯规则基础分需结合特征、命中标签和当时规则版本。

## 37. 人工审核如何保证重复提交安全

先锁订单再锁审核单，已处理记录要求 requestId、动作和审核者匹配；新决策校验到期时间，再按版本与 PENDING 条件更新。相同请求重放返回已有结果，不同语义不应覆盖第一次审核。

项目细节与追问：审核请求幂等还包含审核者，不能让另一个管理员以同号篡改旧动作。审批日志可审计动作，但不是全部规则变更审计。

## 38. 审批成功而自动支付失败会怎样

审批事务已提交，attempt 失败不能回滚审批。重放相同审批请求可以再次触发 attempt；但系统没有自动支付专用持久化重试任务。消费 PASS 的 afterCommit 失败也可能留下 WAITING_PAYMENT，不能说 MQ 重投必然补付。

项目细节与追问：可靠触发和安全执行是两个维度：当前 attempt 可安全重入，但没有独立支付重试队列。准确指出限制比说“最终一致一定完成”更重要。

## 39. 补偿任务扫什么

超时仍为 REQUESTED 的意图、到期订单转 PAY_TIMEOUT、Outbox 重试等，均需幂等。

项目细节与追问：恢复扫描超两分钟 REQUESTED 意图；到期任务处理四种可过期订单态；缓存任务刷新配置。不要把 Redis pending ZSET 当作唯一恢复入口。

## 40. 电子票如何保证不重复出

ISSUE 消费幂等 + tb_issued_ticket UNIQUE(order_id,sequence_no) + 订单 PAID→ISSUED CAS。

项目细节与追问：sequence_no 从订单数量逐一生成，复合唯一键对应同一订单的第几张票。唯一性不等于实现了实名入场、转让或核销系统。

## 41. Workflow 与 Agent 审计是否完全打通

Java 工作流表记录节点与摘要，risk_decision 保存 Agent 六字段结果。Python 完整工具 trace、每轮 token、prompt_version 没有自动完整落入这些表。表存在与字段存在都不代表实际采集完整，订单状态仍是交易依据。

项目细节与追问：Java workflow 的 checkpoint 保存 Java 节点状态，不是 Python LangGraph checkpoint。两个名称相近的概念在面试中尤其容易混淆。

## 42. 幂等的几种层次

客户端 request_id、业务指纹、DB 唯一约束、状态机 CAS、消费记录、成功业务键 success_key。

项目细节与追问：幂等要按副作用逐项说明：预占、落单、发送、消费、支付、出票、释放。一个 requestId 不能包办所有生命周期的去重。

## 43. 分布式锁能替代唯一约束吗

不能作为唯一手段。锁会过期/误删；唯一约束是最后防线。锁可降冲突，约束保正确。

项目细节与追问：当前核心路径主要靠行锁、条件更新和唯一约束，不应把项目讲成全链路 Redis 分布式锁实现。存在解锁脚本也不代表每条路径都调用。

## 44. 什么情况下会用行锁 FOR UPDATE

自动支付确认锁订单，串行化同一订单的并发确认，再配合唯一约束。

项目细节与追问：意图创建还会锁 SKU，审核先锁订单再锁审核单。统一锁顺序有助于降低死锁，但不能据此保证绝无死锁。

## 45. 读写分离适合你们库存扣减吗

扣减必须走主库条件更新。读目录可缓存；库存读可用 Redis，但真相在 MySQL。

项目细节与追问：支付后立即查询或幂等重放需要考虑副本延迟。当前源码没有读写分离配置，读主库是现状；分库方案只作为讨论。

## 46. 当前真的把所有外部 HTTP 移出事务了吗

没有。锁票入口不调用 Agent，但带事务的 TicketEventConsumer 锁订单后会在 REVIEW 分支调用 Python；Wallet 兼容支付也可能在事务内评估。独立自动支付事务减少部分耦合，不能消除这段远程等待。

项目细节与追问：REQUIRES_NEW 也可能额外占用连接，不能把事务拆得越多越好。需要按原子性、锁范围、恢复责任共同判断。

## 47. 事务内调用 Agent 有什么具体代价

连接和订单锁会跨 HTTP 等待持有，服务变慢时消费线程、连接池与同订单操作都可能排队。Java 读超时 2 秒限制单次等待，但不是完全异步隔离。当前仅 REVIEW 调用减少影响面，并未根治长事务问题。

项目细节与追问：连接超时和读取超时不是总交易超时；Python 内部多轮调用也有独立预算。跨层超时不协调会出现 Java 放弃但模型仍继续工作的情况。

## 48. 如何设计可重试服务方法

副作用依赖幂等键；重试安全；区分业务拒绝与系统失败；MQ 用 RECONSUME 策略。

项目细节与追问：请求处理失败后先查询已提交事实再重试。对余额不足等业务结果盲目重试没有意义，基础设施失败则需要安全幂等入口。

## 49. 接口幂等与内部幂等如何配合

入口校验 request_id；内部 Lua/DB/支付键兜底。即使入口漏检，下层仍不产生双份履约。

项目细节与追问：入口 userId 比较防身份替换，指纹防同号参数替换，数据库防多份持久化；这三种校验保护的对象不同。

## 50. 哪些地方是乐观锁 哪些是悲观锁

订单状态和规则编辑比较旧 version，属于明确的乐观条件更新；支付、审核和意图创建存在 FOR UPDATE。库存扣减比较 remaining_stock、销售状态与时间，虽递增 version 却不比较旧值，不能把它描述成版本 CAS。

项目细节与追问：只看表中有 version 不足以认定乐观锁，必须看 WHERE 是否比较版本。钱包余额扣减同样应按具体条件 SQL 解释。

## 51. 库存超卖的典型 bug 有哪些

先读后改无条件、释放两次、缓存回填错误、事务外扣减、消费重复加库存。本项目用 Lua+CAS+HELD 针对这些。

项目细节与追问：排查超卖应还原创建与释放两边。只验证扣减路径，很容易遗漏取消、退款或补偿重复增加库存的问题。

## 52. 限购为什么两边都做

Redis 快速拒绝；MySQL tb_user_purchase CAS 防绕过与缓存不一致。

项目细节与追问：限购计数释放后会减少，语义更接近有效占用数量，不是用户一生累计购买总数。退款是否恢复购买资格需按该实现说明。

## 53. 订单过期如何处理

后台任务扫 expires_at，状态机转到 PAY_TIMEOUT 并 RELEASE，避免占库存。

项目细节与追问：扫描周期为约 5 秒，不是到 expires_at 瞬间必定执行；积压和锁等待还会增加延迟。时间到期和状态变更之间存在窗口。

## 54. 取消与阻断的共同点

都要释放预占库存且幂等；订单进入取消/阻断终态，不能再支付成功。

项目细节与追问：MySQL 释放与 RELEASE Outbox 同事务，Redis 随消费最终回补。因此取消返回后 Redis 库存不一定立即可见增加。

## 55. afterCommit 支付失败是否一定会被恢复

不能保证。消费事务可能已经保存 DONE，重投 RISK_CHECK 会直接返回，现有后台任务没有扫描 WAITING_PAYMENT 自动补付。固定支付键保证安全重试，但还需要可靠触发才能实现最终完成；这两件事要区分。

项目细节与追问：优先复现外层提交成功、支付新事务失败这一断点，再核对 DONE 和 WAITING_PAYMENT。不要用一般 Outbox 重试测试替代这条验证。

## 56. 按源码讲一下 Consumer 的执行顺序

先校验 type 与 messageKey，再锁订单，查询已有消费记录；存在则返回。否则插 PROCESSING，执行 RISK_CHECK、ISSUE 或 RELEASE，最后标 DONE 并提交。不是先无锁插记录，也不是仅捕获重复键就代表所有异常成功。

项目细节与追问：ISSUE 只在 PAID 时创建电子票，其他状态可以无副作用完成消费。这是状态守门的一部分，不等于消息参数完全无需校验。

## 57. 若 SENT 后一直无消费记录

Publisher/补偿可对超时未 DONE 的消息再投递；消费幂等保证安全。

项目细节与追问：SENT 超五分钟且不存在 DONE 记录时重排。若 DONE 已有但之后的 afterCommit 支付失败，该补偿不会识别为未消费。

## 58. RocketMQ Topic 与 producer group

业务 topic ticket-events；producer group ticket-outbox-producer（见配置）。面试记「Outbox 投递」即可。

项目细节与追问：consumer_group 也参与数据库唯一键，不能随意改组名后认为业务去重沿用旧记录。物理消费组与业务记录命名需要一起核对。

## 59. 当前指标可以证明哪些事情

Actuator 和业务计数器反映服务状态与部分业务结果，管理接口也汇总审计字段。但 Python 每轮 usage 未完整采集，不能把 LLM 汇总当真实全部 token 成本。指标需要与订单、Outbox、消费记录及日志关联解释。

项目细节与追问：建议观察库存、支付、Outbox 与 Agent 不可用率属于面试讨论；本次没有建立新告警，不将建议当成现有运营能力。

## 60. 日志里为什么要 traceId

跨抢票、消费、支付、出票关联一次请求，排障必备。

项目细节与追问：traceId 是相关性标识，不是请求幂等键，也不是分布式事务 ID。即使日志缺失，数据库约束仍应维护正确性。

## 61. 统一异常与业务错误码怎么做

BusinessException 携带业务码如 429 限流；全局处理成 Result，避免把堆栈直接给前端。

项目细节与追问：Result 字段为 success、errorMsg、data、total，非空策略会省略 null。权限拦截器的空响应与 Controller 的统一包装需分别处理。

## 62. 校验用在哪一层

入口 Bean Validation；领域状态机；DB 约束。三层互补，不单靠前端。

项目细节与追问：quantity 的接口上限是 100，但 SKU purchase_limit 可能更小。通过 Bean Validation 不代表库存、限购和业务状态也通过。

## 63. 配置外置哪些关键项

DB/Redis/MQ、agent url/key、outbox 重试、jobs 开关、线程池、demo 登录开关。

项目细节与追问：application.yml 默认端口不等于 Compose 全部主机映射。文档给配置示例应使用占位符，不能复制实际私有密码与密钥。

## 64. initialization-mode 为 never 意味着什么

Java 启动不自动执行 schema.sql 和 data.sql。Compose 把这两个脚本挂到 MySQL 首次初始化目录，只对空数据目录生效。已有数据卷不会因代码更新自动迁移，需要检查实际库结构与版本。

项目细节与追问：空库初始化与已有库升级是不同操作。误删数据卷来“应用 schema 变更”有破坏性，不能作为常规文档指令。

## 65. V100 和 V101 文件存在是否等于启用 Flyway

不等于。文件分别提供结构和种子数据材料，但当前 POM 未配置 Flyway 依赖，不能宣称自动发现、校验和执行迁移。文档应说“存在迁移脚本”，并把真实初始化方式与运维步骤另列。

项目细节与追问：命名 V100/V101 可以保留迁移材料，但执行器、版本历史表和升级策略要独立确认，不能由文件名推导运行行为。

## 66. 金额字段为何用 DECIMAL

避免 double 误差；库表 amount/price/balance 均为 DECIMAL。

项目细节与追问：Java 交易金额用 BigDecimal，风控特征中可能转 double 仅用于评分。不要把评分计算的近似数值再作为余额账本更新值。

## 67. 为何 payment success_key 可空

非成功态可不占成功键；成功时写入，UNIQUE 允许多个 NULL（MySQL 行为），需确保成功路径必写。

项目细节与追问：NULL 与空字符串不同：空字符串会占唯一值。成功路径必须稳定生成业务键，不能靠客户端提供任意 success_key。

## 68. 用户角色如何保护管理操作

登录态中的 UserDTO 提供身份和角色，管理拦截器对 /api/admin/** 与指标相关路径要求 ADMIN。用户订单操作还校验所有者。角色判断是服务端责任，前端隐藏按钮不能替代它；拦截器拒绝可能只有 HTTP 状态而无 Result JSON。

项目细节与追问：Demo 登录开关开启会返回验证码，便于演示但不是生产短信登录。UserDTO 与原始用户表返回也要区分，避免暴露多余字段。

## 69. 缓存能缓存订单状态吗

可短 TTL，但支付/出票以 DB 为准；轮询可靠来源是订单 API 读库或读主。

项目细节与追问：订单列表当前返回最多 100 条，详情读订单与票。缓存订单状态会引入读一致性问题，不能用过期缓存判断是否允许支付。

## 70. 前端轮询 vs WebSocket

Demo 用轮询简单可靠；高实时可推送，但要处理断线与状态对账。

项目细节与追问：轮询必须同时识别成功、审核、阻断、取消和超时，避免永不停止。当前未实现 WebSocket，推送方案要明确标为扩展讨论。

## 71. 安全上 Agent 调用注意什么

内网+共享密钥；超时；不把交易写权限给 Python；校验返回字段范围。

项目细节与追问：Python 返回范围校验与 Java Map 数字截断是两层不同控制。Java 不会自动继承全部 Pydantic 嵌套规则。

## 72. SQL 注入如何防

JdbcTemplate 参数绑定；避免拼接用户输入。动态排序等需白名单。

项目细节与追问：Repository 中 LIMIT 拼接使用内部受控整数；若将来开放用户排序或字段名，参数绑定不能替代标识符白名单。

## 73. 项目是否已经实现密码哈希与完整脱敏

当前主要是 Demo 验证码登录，虽然有 password 字段，不能声称已实现密码登录与哈希方案。接口、日志和审计包含业务上下文，也没有覆盖全链路脱敏的证据。面试应将安全设计原则与实际已落地能力分开。

项目细节与追问：不要在面试演示中展示环境中的真实 token 或密码。源码可证明共享密钥校验，不能证明密钥轮换、吊销和审计机制已完备。

## 74. 自动支付如何处理并发唯一冲突

先锁同一订单，再查询固定 paymentRequestId 和状态，合法时插入支付行，数据库唯一键兜底。当前不是“捕获所有重复键然后返回旧记录”的通用实现；不匹配的请求语义或异常会失败，应以事务回滚与再次查询核实结果。

项目细节与追问：并发失败的 HTTP 次数不等于业务重复次数，应查看提交后的支付行、余额和流水。数据库异常处理路径也需要真实库验证。

## 75. 为什么不先 select 再 insert 做幂等

有竞态窗口。必须靠 UNIQUE，先查只是优化。

项目细节与追问：先查再写可减少普通重放开销，不能消除两个事务同时读到不存在的窗口。必须设计冲突后的回滚与重试语义。

## 76. 连接池打满常见原因

事务内远程调用、慢 SQL、未释放连接、并发过高。对应：拆事务、索引、池监控。

项目细节与追问：本项目 REVIEW HTTP 持锁是一个具体排查入口。先用线程栈、连接池等待和 SQL 时长关联，再决定是否需要优化。

## 77. 慢 SQL 可能点

补偿扫无索引、订单过期扫、outbox due 索引是否命中。已有 idx_outbox_due、idx_request_recovery 等。

项目细节与追问：有索引不代表执行计划一定使用，数据分布、联合索引顺序与范围条件都影响结果。没有 EXPLAIN 或实测就不要宣称查询性能已保证。

## 78. 测试如何区分替身和真实中间件

普通单测可用 H2、Mock 或脚本化依赖；Testcontainers 集成测试才提供容器级证据，还应核实启用 profile 与 skip 条件。不能把 mvn test 的成功自动解释为真实 MySQL、Redis、RocketMQ 并发全链路已通过。

项目细节与追问：报告应给出执行命令、时间、用例数、失败和跳过原因。本次只生成文档，不沿用旧版“75 tests”数字作为现在的验证结论。

## 79. 单测重点覆盖什么

状态机边、自动支付幂等、Outbox、重复消费、库存 CAS、规则决策 clamp。

项目细节与追问：状态机非法边、Agent 负分归零、租约失效回写和重复 ISSUE 等是有意义的行为测试；只断言 getter/setter 不能证明交易正确。

## 80. WalletConcurrencyTest 还保留意义

兼容路径回归；但面试主叙事应讲 AutoPayment，不把钱包 CAS 当主亮点。

项目细节与追问：自动支付不扣钱包，因此 WalletConcurrencyTest 通过不能证明主链 afterCommit 恢复正确。两套路径应分别描述覆盖目标。

## 81. 如何描述你们的一致性模型

单库本地事务强一致；跨 MQ 最终一致；Redis 预占与 MySQL 对账靠事务+补偿。

项目细节与追问：跨 Redis/MySQL 的一致性依赖意图与释放恢复，不是全局事务。最终一致也有前提：任务运行、数据未损坏、重试入口可达。

## 82. 能否给整个项目贴 CP 标签

不宜。CAP 讨论的是发生网络分区时一致性与可用性的选择，需要指定系统边界。这里单库事务、Redis 预占与 MQ 最终一致性并存；库存条件更新偏向正确性，但一句“全系统 CP”不能解释缓存与账本的恢复机制。

项目细节与追问：可以具体回答故障时拒绝新预占、保留 MySQL 约束、恢复消息重投，比抽象贴标签更符合工程事实。

## 83. 如何扩展到多 SKU 购物车

需要更大聚合事务或 TCC/Saga；当前模型是单 SKU 预占，要重新设计锁顺序与幂等键。

项目细节与追问：多 SKU 会带来多行锁顺序、部分预占成功补偿和跨槽 Lua 问题。当前 request 指向一个 SKU，不能复用单 SKU 原子脚本就宣称支持购物车。

## 84. 多机房怎么考虑

Outbox/库存强依赖中心主库；跨区域需同步策略。当前 Demo 单区域。

项目细节与追问：Compose 描述的是本地部署，没有跨机房一致性、故障切换与灾备演练证据。面试应将这些作为边界而不是经历。

## 85. 若要接入微信支付宝，键如何复用

渠道支付单号映射 payment_request_id；成功回调写 success_key；状态机 WAITING_PAYMENT 可接异步回调。

项目细节与追问：第三方回调还需验签、金额校验、渠道订单对账和重复通知处理。当前自动支付只具备部分内部幂等积木，不是可直接上线的渠道适配器。

## 86. 限流算法用什么

Redis ZSET 滑动窗口 Lua，用服务端时间，避免客户端时钟漂移。

项目细节与追问：窗口写入使用 Lua 服务端时间；部分读取 count 使用 Java 当前时间。不能把全链路所有时钟都说成统一 Redis 时钟。

## 87. 令牌桶和滑动窗口怎么选

窗口更直观做「每分钟次数」风控；令牌桶更平滑。本项目窗口服务 rateLimit。

项目细节与追问：滑动窗口用 ZSET 删除过期记录并计数，易理解但成员数量带来内存成本。选择依据是当前频率特征语义，不是算法绝对优劣。

## 88. 如何防止黄牛刷接口

设备/IP/用户频率规则、黑名单、限购、审核、Agent 关联账户调查（REVIEW）。

项目细节与追问：跨事件证据字段虽已支持，Java 尚未自动装配，不能夸大实际账号团伙识别效果。规则与限购才是当前可直接解释的确定性措施。

## 89. 设备指纹只靠 deviceId 够吗

不够，可伪造。需组合行为与关联图谱；Agent 工具看关系与流转，但仍是辅助。

项目细节与追问：同设备或同 IP 只能构成关联信号，家庭、公司网络也会共享。规则阈值和人工审核需要避免把相关性当欺诈证明。

## 90. 数据归档策略

订单/outbox/consume 按时间分区或归档冷存储；Demo 未做，可作改进点。

项目细节与追问：归档不能提前删除幂等记录，否则旧消息重放可能重新执行。保留期要与消息重试、业务追溯期共同设计；当前未实现自动归档。

## 91. 删库跑路式面试题：最怕哪个 bug

双释放加库存、支付成功两次出两票、风控未过却支付。对应 HELD、success_key、PASS/APPROVE 门禁。

项目细节与追问：资金语义错配同样关键：自动确认未扣钱包而退款加款。它不是吞吐量问题，性能测试无法代替业务正确性审查。

## 92. 面试中如何讲一次并发排查

先给出自己实际有记录的复现和证据，不虚构故障经历。可用本项目设计一个分析案例：在消息发送后、标 SENT 前模拟中断，核对重投是否只生成一份票，再检查消费记录与唯一约束。没有实际跑过就标明是验证方案。

项目细节与追问：回答必须区分“我实际复现过”和“我会这样排查”。本册提供可验证的思路，不替读者虚构项目个人贡献。

## 93. Service 层事务注解要注意什么

自调用绕过代理；私有方法无效；异常类型回滚规则；传播与只读。

项目细节与追问：Spring 默认通常对 RuntimeException 回滚，受检异常需按配置判断。当前 BusinessException 的传播与回调异常要结合实际事务边界分析。

## 94. 当前只读事务与隔离级别怎么说

查询入口不应一概宣称加了 readOnly，需检查具体注解。明确可确认的是意图创建使用 READ_COMMITTED 和独立事务，并对 SKU 加行锁。隔离级别不能替代唯一约束，也不能消除所有死锁。

项目细节与追问：事务隔离只作用于数据库，不会把 Redis Lua 或 HTTP 自动纳入同一事务。跨资源副作用仍需要幂等和恢复。

## 95. 管理端修改规则已经有哪些保护

更新通过 rule_code 与 version 条件防止覆盖，并校验 DECISION_POLICY 的关键字段与阈值关系。当前方法没有完整规则变更审计链；agentMaxAdjustment、rateLimit 等也并非所有边界均显式校验。不要把安全变更流程当作已实现事实。

项目细节与追问：策略变更可立即改变后续判定；risk_decision 保存命中版本但没有完整版本历史仓库，长期可重放性不能仅靠一个 version 字段保证。

## 96. 指标告警建哪些

支付失败率、风控 BLOCK 比、Outbox FAILED、消费延迟、Agent unavailable 比、库存为 0 但仍请求。

项目细节与追问：告警优先关注“有订单无推进”“库存不守恒”“重复成功支付”等业务不变量，而不只看 CPU。当前清单是设计讨论，不是已部署告警。

## 97. 容量评估怎么说

先正确性后容量；用 JMeter 方案测业务不变量。不编造未测 QPS。

项目细节与追问：TPS 和 P99 必须附环境、数据量、并发模型与错误口径。本项目名字包含高并发，不等于已经证明某个规模。

## 98. 代码结构如何分层

Controller→Service→Repository；MQ Consumer 调领域服务；Infrastructure 放 Admin/Jobs。

项目细节与追问：Controller 仍有少量 Db 查询和管理 SQL，分层不是绝对纯净。可以解释本轮只收敛核心写路径，避免宣称完全无跨层访问。

## 99. 为什么 Consumer 不直接写一大段 SQL

便于单测与复用（释放、审核、支付）。事务边界仍在服务方法。

项目细节与追问：Repository 使 SQL 条件可集中审查，Service 仍负责事务与流程。不应把关键状态判断全部丢给数据库层而失去业务可读性。

## 100. 总结后端面试主线三句话

Lua+MySQL 防超卖；Outbox+消费幂等做最终一致；fast 准入后自动支付用唯一键保证只确认一次、只出票一次；Agent 仅深度 REVIEW 辅助画像且不能降分，永不决定当前订单支付。

项目细节与追问：最后补一句边界：这是自动确认的 Demo，真实资金、完整 Agent 审计与自动支付失败恢复尚有缺口；用证据表达能力而不是堆组件。
