# 架构决策与数据库字段取舍文档

## 1 文档性质与判断依据

本文根据当前源码整理 33 项决策与取舍，采用“现状、备选、代价、验证点”的结构。除代码直接体现的采用状态外，理由是对工程影响的分析，不冒充原作者历史会议记录；没有实现的能力明确指出。文档并非新一轮开发计划。

本文依据 2026年9月17日工作区源码、DDL、配置与现有测试源码整理。它是源码说明，不是本次真实环境验收报告；未重跑的测试、容器状态、吞吐量和模型效果均不作为已验证结论。

## D01 Java 交易终裁与 Python 调查分离

现状与范围：订单、库存、消息、支付状态都由 Java 写入；Python 只返回调查建议。深度分析结果由 Java 写入 `tb_risk_profile`，供后续请求的 fast 准入读取；**不回头改当前已成功订单**。

备选与取舍：可选让 Agent 同步闸门当前订单，或纯规则无 Agent。本项目将准入与画像更新解耦，避免慢调查拖垮抢票与履约。

代价与限制：已放行的订单若事后画像升高风险，只能影响后续请求，不能自动撤销本单（需人工/运营流程另议）。

源码和验收要点：看 `RiskDecisionService.fast` / `evaluate`、`RiskProfileService`、`TicketEventConsumer` 对 RISK_CHECK 的处理。

## D34 RiskProfile 持久化与热缓存

现状与范围：`tb_risk_profile` 按 USER/DEVICE/IP 存 decision/score/expires；Redis `risk:profile:*` 热缓存；`source_decision_id` 幂等。

备选与取舍：仅用黑名单或仅用决策流水表。独立画像表让 fast O(1) 读取主体风险，无需扫历史决策。

代价与限制：Redis 写失败不回滚 MySQL；缓存可重建。过期画像视为无效。

源码和验收要点：`JdbcRiskProfileRepository`、`RiskProfileCache`、`RiskProfileSemanticTest`。

## D02 保留 Java 8 与 Spring Boot 2.3

现状与范围：源码及构建基线沿用旧运行时，当前重构未迁移整个框架。

备选与取舍：继续现有版本减少改造面；升级可能带来维护与生态收益，但需要处理驱动、Redis、MQ starter 和行为兼容。

代价与限制：不能把“少改”说成长期无需维护；显式覆盖依赖版本也要求额外兼容检查。

源码和验收要点：版本来自 pom.xml，没有可验证的原始选型会议纪要。本文解释影响，不杜撰当年团队决策历史。

## D03 显式 JDBC Repository

现状与范围：交易 SQL 放在 Repository 实现中，服务负责事务和编排，部分查询仍用 Db/Map。

备选与取舍：JPA 与 MyBatis 也支持条件更新；当前 JDBC 让库存条件、订单版本和租约 token 直接可见，并避免全量 ORM 迁移。

代价与限制：需要维护 SQL、字段映射和数据库方言测试；类型化并未覆盖所有接口。

源码和验收要点：用真实 SQL 与并发测试验证，不用“某 ORM 天生不安全”来论证选型。

## D04 有限 Typed Model

现状与范围：TicketOrder、ReservationIntent、TicketSku 等需要整行读取的对象使用类型模型，纯原子写接口不为形式制造空对象。

备选与取舍：全 Map 更灵活但易拼错字段；全量领域建模更统一但本轮成本大。采用按需求类型化的中间路线。

代价与限制：仍存在 Map 与对象混合，以及响应字段风格不一；不是完整 DDD 或全量不可变模型。

源码和验收要点：类与 Repository 对应关系可查源码。RiskContext 的 final 字段也不意味着内部 Map 深不可变。

## D05 Redis Lua 与 MySQL 双层库存

现状与范围：Lua 原子检查销售窗、配额、库存和预占指纹，MySQL 条件减与配额表守住持久化事实。

备选与取舍：只用 Redis 恢复风险大；只用 MySQL 可减少跨系统一致性问题，但热点排队需评估。当前保留两层。

代价与限制：增加意图、释放与恢复复杂度；同步链路仍有 SKU 行锁与 SQL，不是无锁纯缓存方案。

源码和验收要点：防超卖需同时测创建与释放，不能只报成功请求数。吞吐量收益必须实测，不从架构名称推导。

## D06 保留 total_stock 与 remaining_stock

现状与范围：总量表达销售容量，剩余量用于条件扣减，两者同时存在以支持数量约束与管理操作。

备选与取舍：只存总量然后聚合订单可减少冗余，但热点查询与并发判断复杂；只存剩余量难解释容量变化。

代价与限制：冗余字段需要更新规则，CHECK 只覆盖部分不变量；取消、退款与补偿错误仍可能破坏总量语义。

源码和验收要点：DDL 声明 remaining>=0、total>=remaining；实际库是否执行对应约束需要运行验收。

## D07 user_purchase 单独维护配额

现状与范围：以 user_id+sku_id 复合主键保存有效占用量，与 Redis 用户计数互为防线。

备选与取舍：实时聚合所有订单可避免独立计数，但查询与并发更新更重；只用 Redis 会缺持久化配额事实。

代价与限制：释放时必须同步减少；该量不是用户终身购买次数。若改变退票后是否恢复资格，需重新明确语义。

源码和验收要点：业务条件 UPDATE 与 reservation 首次释放共同约束，不依赖全链路分布式锁。

## D08 requestId 与 fingerprint 双标识

现状与范围：requestId 标识受理请求，fingerprint 校验同号业务参数，摘要含用户、场次、SKU、数量、设备。

备选与取舍：只看 requestId 无法发现参数偷换；把所有字段拼成主键则难以维护且会泄露上下文。

代价与限制：MD5 不构成安全签名；IP 不在摘要中；换请求号仍是新尝试，需要配额与身份控制。

源码和验收要点：同号同参重放与同号异参拒绝应分开测试，不能宣称指纹阻止所有重复购买。

## D09 持久化意图与预分配 ID

现状与范围：Redis 操作前以 REQUIRES_NEW 写 REQUESTED，提前生成 reservation_id 和 order_id。

备选与取舍：如果只在成功订单中留记录，Lua 成功后进程崩溃就缺恢复定位。先写意图增加一次提交以换取可恢复性。

代价与限制：意图可能长期存在失败记录，扫描、保留和重试语义需要管理；当前补偿阈值为两分钟。

源码和验收要点：字段并非“成功后回填”。恢复孤儿只释放 Redis 并标失败，不能重复增加已经回滚的数据库库存。

## D10 reservation 与 order 分表

现状与范围：reservation 表达占用及 HELD/RELEASED，order 表达风控、支付和履约状态，两者唯一关联。

备选与取舍：合表更少连接，但库存释放资格与交易多阶段状态会耦合；当前分表让首次释放守门独立。

代价与限制：维护关联与双重状态需要更多代码，不能只改订单 CANCELLED 而忘了预占释放。

源码和验收要点：order.reservation_id 有物理外键和唯一约束；其他关联未必声明物理外键。

## D11 version 与条件更新共存

现状与范围：订单迁移比较旧 status/version；规则编辑比较版本；库存减量根据 remaining、状态、窗口。

备选与取舍：悲观锁适合组合检查，乐观条件更新适合拒绝过时写；当前两者并用。

代价与限制：version 自增不一定参与并发比较，不应统一称全部“版本乐观锁”。多锁操作还需关注锁顺序。

源码和验收要点：判断依据是 WHERE 子句。字段命名和实体注解不能代替 SQL 证据。

## D12 Outbox 而非数据库提交后直接发 MQ

现状与范围：消息登记与业务同事务，Publisher 之后领取并发送。

备选与取舍：直接双写简单但有丢消息窗口；RocketMQ 事务消息也是一种可选机制，但当前项目没有采用其回查流程。

代价与限制：新增消息表和扫描成本，传输仍可能重复；Outbox 解决的是可靠登记，不是所有后续动作必然成功。

源码和验收要点：append 的 MANDATORY 是事务要求，不能在没有业务事务时把消息当作成功事实发送。

## D13 message_key 使用 type 加 orderId

现状与范围：同一订单的 RISK_CHECK、ISSUE、RELEASE 各对应稳定业务键。

备选与取舍：随机消息键适合独立事件，却不能天然去重同一业务动作；现有键使唯一性可由数据库直接约束。

代价与限制：限制了同订单同类型多次事件的表达；未来若需要分批出票或多次释放，必须重新设计版本/批次语义。

源码和验收要点：当前只支持全量单次语义，不能据此推断已有分批履约能力。

## D14 租约令牌与到期时间

现状与范围：lease_token 标识拥有者，next_retry_time 兼做租约到期或下一重试时刻，状态区分含义。

备选与取舍：单机锁不能协调多实例；固定“正在发”状态不能恢复崩溃工作者；数据库条件领取无需新增中间件。

代价与限制：字段复用降低表复杂度但读写语义要随状态理解；租约过期仍可能产生重复网络发送。

源码和验收要点：所有回写带 token 条件。验证旧租约工作者不能覆盖新状态，同时验证消费者可承受重投。

## D15 独立消费幂等表

现状与范围：consumer_group+message_key 与 group+business_key 约束同一组的有效处理，DONE 与业务事务一同提交。

备选与取舍：只依赖 Broker 消息 ID 不适合业务重投；只判断订单状态不易解释多个事件阶段。

代价与限制：幂等记录有存储与保留成本，提前清理会打开旧消息重放窗口。

源码和验收要点：当前 DONE 不覆盖提交后的自动支付事务，不能把消费成功扩大解释为全链路履约已完成。

## D16 Demo 自动确认与 Wallet 兼容

现状与范围：风险通过后自动写 PAYMENT SUCCESS，不扣钱包；Wallet 手动支付和退款仍保留。

备选与取舍：自动确认简化演示，钱包可展示资金条件更新，真实渠道需要更多回调与对账工作。

代价与限制：自动确认并非真实收款，当前退款未按来源分流，会给钱包加订单金额；有资金语义错配风险。

源码和验收要点：这是源码可见限制，本次不修。进入真实支付场景前，必须先定义原始资金来源及退款对应关系。

## D17 双支付幂等键与可空 success_key

现状与范围：payment_request_id 控制同一尝试，success_key 控制同订单同动作的成功事实；非成功尝试允许 NULL。

备选与取舍：只用请求号挡不住换号再成功；只用成功键无法完整保存失败尝试与其重放结果。

代价与限制：依赖成功路径稳定写键；可空字段不代表成功也可以随意不填。自动支付和钱包共用命名空间。

源码和验收要点：MySQL UNIQUE 可容纳多个 NULL；空字符串不同。测试应核对一笔有效成功以及余额、ledger 一致。

## D18 afterCommit 加 REQUIRES_NEW

现状与范围：外层风险事务提交后触发新支付事务，使未提交的 PASS 不会产生支付；支付与 ISSUE 原子落库。

备选与取舍：同事务支付减少提交点却扩大耦合；线程池直接 fire-and-forget 仍需考虑提交时机与持久化触发。

代价与限制：当前 afterCommit 同线程执行，失败时外层已提交；没有持久化支付重试调度，RISK_CHECK DONE 可能阻止再触发。

源码和验收要点：“可安全重试”不等于“系统一定重试”。单测幂等与崩溃恢复测试是不同验收项。

## D19 金额用 DECIMAL 与 BigDecimal

现状与范围：订单、价格、钱包、支付和流水采用 DECIMAL(18,2)，交易计算使用精确金额对象。

备选与取舍：double 易有二进制小数误差；以最小货币单位整数也可行，但当前字段与代码已有精确小数约定。

代价与限制：金额范围、小数舍入、币种和汇率尚未形成多币种模型；风控特征转换 double 不能用来回写账本。

源码和验收要点：说明当前只处理固定精度金额，不把简单 Demo 金额字段说成国际支付账务平台。

## D20 保留 frozen_balance 与 ledger

现状与范围：钱包表含冻结字段，流水与 payment transaction 关联，自动确认不写支付钱包流水。

备选与取舍：保留字段避免破坏兼容模块；删字段可减少歧义，但需先确认历史依赖与数据迁移。

代价与限制：冻结字段存在不等于实现冻结、解冻和结算；ledger 也不能解释没有实际扣款的 AUTO_PAY。

源码和验收要点：当前文档明确标为兼容或未参与主链，不通过补写虚假流水掩盖资金语义问题。

## D21 规则存配置文本加策略注册

现状与范围：规则编码、权重、config、version 存表，Java 策略解释特征阈值，Registry 保证选择唯一。

备选与取舍：硬编码简单但难调整；任意表达式或脚本引擎灵活但增加执行面和校验成本；当前只提供受控策略。

代价与限制：TEXT 配置需应用校验，未支持任意规则 DSL；无匹配策略会跳过，策略重叠报错，需要配置测试。

源码和验收要点：不能从“可扩展策略”推导已实现大量不同算法；当前主要是 GenericThresholdRuleEvaluator。

## D22 只有 REVIEW 调 Agent

现状与范围：明确 PASS/BLOCK 跳过 Python，灰区通过调查增加证据。

备选与取舍：全部调用增加成本与等待；完全规则化减少不确定性但缺少动态证据组合。当前在灰区引入可降级建议。

代价与限制：调用仍在消费事务与订单锁内，复杂调查受 Java 两秒读取限制；不是完全异步旁路。

源码和验收要点：无 Agent 时规则独立决定，REVIEW 不自动 PASS。实际性能与模型价值仍需分别验证。

## D23 非负有界调整与 Java 终裁

现状与范围：Python 合同允许 -20..20，Java 仅接受非负 cap 增量，随后重新计算阈值并检查黑名单。

备选与取舍：允许负分可降低误拦却扩大模型放行权；当前约束保持规则风险底线。

代价与限制：可能保留规则误拦，不能借 Agent 纠正低估之外的问题；confidence 不参与门控，效果需评测。

源码和验收要点：初判 REVIEW 不能因负分变 PASS。riskLevel 与 suggestion 是建议，不是可执行状态指令。

## D24 可选历史列表不新增采集表

现状与范围：historicalEvents、ticketFlows、linkedAccounts 默认 None，旧请求继续解析。

备选与取舍：增加数据库表和历史平台能提供证据，但超出当前应用层合同演进；请求装配保持改动有限。

代价与限制：Java 当前尚未装配列表，工具只读本次请求，因此调查能力受数据可得性限制。

源码和验收要点：None 不等于清白。支持生命周期输入不等于已经实现转票、核销、实名变更接口。

## D25 LangGraph 条件编排与职责工具隔离

现状与范围：两路调查并行，Analyst 无工具，必要时定向回查；工具映射分别封闭。

备选与取舍：单 Prompt 更简单；手写循环也能实现；LangGraph 显式表达状态与条件边便于理解和测试。

代价与限制：额外框架与状态合并复杂度；多 Agent 不天然提升准确率或安全性。

源码和验收要点：测试应检查分支、合流、focus、计数和未知工具，而非只检查三种类名存在。

## D26 有限轮次与降级

现状与范围：一次调查模型循环最多 4 次，总再调查最多 2 次，异常返回 unavailable。

备选与取舍：无界循环可能不收敛；过早终止降低证据质量；当前硬上限优先结束与降级。

代价与限制：一次可有多个工具调用，缺 max_tokens、历史长度限制和整图 deadline；强制 sufficient 不保证证据充分。

源码和验收要点：HTTP 200 fallback 不是模型成功，计数器和效果报告应区分。

## D27 JSON 文本快照而非原生 JSON 列

现状与范围：features、matched_rules、agent_analysis、workflow 输入输出采用 TEXT/MEDIUMTEXT 存储序列化快照。

备选与取舍：原生 JSON 列可提供数据库验证和路径查询；拆明细表利于统计却增加结构与迁移成本。

代价与限制：当前数据库不验证内部 JSON 结构，查询与升级由应用承担；没有完整历史规则版本表就不能保证任意旧决策完全回放。

源码和验收要点：字段字典应写 TEXT 中的 JSON，不写成原生 JSON。score 当前只保存调整后值。

## D28 工作流审计复用而非新建 Agent 平台

现状与范围：Java workflow 与 audit 表记录节点和摘要，Python 内部 trace 没有完整透传和持久化。

备选与取舍：复用可减少表和组件；专门模型观测系统更全面但增加集成和数据治理成本。

代价与限制：token_count、prompt_version、cache_hit 字段存在不代表已采集；Java checkpoint 不等于 LangGraph 持久化恢复。

源码和验收要点：本轮文档纠正能力描述，不新增审计平台、工具或表来填补叙述。

## D29 有限物理外键与应用关联

现状与范围：DDL 只有三处物理外键，大部分 order/user/workflow 引用依赖应用维护，唯一键负责部分身份关系。

备选与取舍：更多外键增强数据库一致性，但增加迁移和写入约束；无外键则需要更强应用与对账保障。

代价与限制：当前没有证据表明曾系统性评估全部外键取舍，不能编造“为性能而全部去外键”的历史。

源码和验收要点：区分已声明外键、唯一关系与普通索引。索引加速关联，不强制被引用行存在。

## D30 时间字段与动态状态

现状与范围：销售窗口、到期、重试、创建和更新分别存时间，任务按阈值扫描，订单按状态 CAS 推进。

备选与取舍：把到期直接编码进 Redis TTL 简单但难做持久化恢复；单靠数据库扫描有调度延迟，当前两者分工。

代价与限制：TIMESTAMP 受数据库时区语义影响；部分 updated_at 仅默认创建值，需代码显式更新。自动支付执行器内没有独立到期校验。

源码和验收要点：不能用“到期即瞬时关闭”描述周期扫描。时间与状态竞态应在 correctness 验收中验证。

## D31 前端轮询而非实时推送

现状与范围：用户受理抢票后查询订单，审核通过后同样等待自动确认与出票结果。

备选与取舍：轮询简单且失败可恢复；WebSocket/SSE 降低刷新延迟但增加连接、断线补偿和鉴权复杂度。

代价与限制：短期多次请求、结果延迟和状态终止条件需要处理；当前没有实现推送平台。

源码和验收要点：前端只展示与发请求，不决定库存、风险或支付事实，不能用按钮禁用代替幂等。

## D32 初始化脚本与迁移执行器分开

现状与范围：Compose 在空 MySQL 数据目录执行 schema/data；Java initialization-mode=never，POM 未启用 Flyway。

备选与取舍：首次初始化简单；成熟版本迁移能追踪升级历史，但当前仅有 V100/V101 材料而无执行器。

代价与限制：已有卷不会自动升级，文档和新 DDL 可能与真实库不一致。

源码和验收要点：本次不启动迁移、不删卷，只明确不能把脚本文件名当自动升级证据。

## D33 正确性证据优先于性能叙事

现状与范围：说明测试类型、运行环境、跳过情况，不复用旧数字充当当前结论。

备选与取舍：单测快而可重复，真实中间件测试更贴近故障和并发；性能压测回答容量而非业务守恒。

代价与限制：没有当前验收就不能宣称全部并发性质已证实；源码审查只能指出机制和潜在缺口。

源码和验收要点：本次仅更新文档与生成 Word，不新增功能、不改交易代码、不执行大规模压测。

## 3 最容易误读的字段取舍

| 字段 | 为什么保留 | 不能推导的能力 |
|---|---|---|
| password | 沿用用户表结构 | 已支持密码哈希登录 |
| frozen_balance | 保留钱包兼容模型 | 已支持冻结解冻结算 |
| version | 部分对象版本与变更计数 | 所有更新都比较旧版本 |
| fingerprint | 同请求号参数一致性 | 安全签名或阻止换号购买 |
| success_key | 同订单动作成功唯一 | 真实渠道收款已经完成 |
| agent_analysis | 保存六字段分析摘要 | Python 全部证据和工具轨迹可回放 |
| prompt_version、token_count | 审计字段扩展能力 | 当前所有模型调用已采集 |
| workflow_checkpoint | Java 工作流状态快照 | LangGraph 已持久化与断点恢复 |
| task_id | 复用工作流关联 | 已实现通用任务调度平台 |

## 4 当前工程边界对设计评价的影响

从正确性角度，应首先区分 Demo 确认与真实资金。当前自动支付未扣钱包，而退款未依据原支付来源分流，是最需要明确业务含义的问题。其次是 afterCommit 支付失败没有持久化自动重试触发。它们不是多加一个模型、增加并发线程或提高 TPS 就能解决的问题。

从 Agent 角度，核心边界已经可以在源码中定位：锁票 fast 不调用 Python，evaluate 仅 REVIEW 调用，Java 终裁并非负封顶。但消费事务内 HTTP、可选历史数据未装配、预算与审计不完整，是评价应用成熟度时必须保留的限制。

本册不将这些限制转换成未经授权的修改；它为阅读与面试提供可核对的判断依据。若现场被问“为什么不采用某框架”，优先回答当前约束、替代方案的实际成本以及何时需要重新评估，避免使用绝对优劣判断。
