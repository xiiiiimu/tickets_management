# 接口数据库与工程细节手册

本文依据 2026年9月17日工作区源码、DDL、配置与现有测试源码整理。它是源码说明，不是本次真实环境验收报告；未重跑的测试、容器状态、吞吐量和模型效果均不作为已验证结论。

## 1 阅读约定与响应格式

本文中的路径来自现有 Controller 和 Python 路由，字段字典由工作区 schema.sql 提取，不是线上数据库反查结果。当前 Java 混用类型对象与 JDBC Map，因此请求多为 camelCase，数据库 Map 查询响应多为 snake_case；不能把整套 API 统一描述为某一种命名规则。

Java Controller 通常返回 Result，包含 success、errorMsg、data、total，null 字段可被省略。业务异常返回对应 HTTP 状态；参数错误通常 400，未知运行异常由 WebExceptionAdvice 返回 503 并提示使用相同请求号重试。登录与管理拦截器的 401/403 可能没有统一 JSON 包装。Python 分析接口直接返回 Analysis，不套 Result。

客户端在受保护请求中传 authorization token，服务端从 Redis 恢复用户。管理接口要求 ADMIN，订单接口额外校验所有者。前端展示权限不能代替后端权限。示例中的 ID、token、设备号均为占位值，需要先用现有目录和登录接口获取真实值。

## 2 用户与目录接口

| 方法与路径 | 参数和输入 | 响应与注意点 |
|---|---|---|
| POST /api/user/code | query phone | Demo 验证码流程，受开关控制，不是已接短信网关 |
| POST /api/user/login | JSON phone、code | 返回登录 token；password 字段存在不代表密码分支已实现 |
| GET /api/user/me | 登录 token | 当前 UserDTO |
| GET /api/user/{id} | 数字用户 ID、登录 token | 返回公开 UserDTO，未查到可为空结果 |
| GET /api/events | 公开目录查询 | catalog 返回在售演出 |
| GET /api/events/{id} | 演出 ID | 在售演出附 sessions 与 skus，查无演出为 404 |

目录详情查询演出状态，但附带的 SKU 列表不等于全部当前可预占；实际是否能买仍由 SKU 状态、销售时间、库存和限购校验。新用户注册不会自动创建 wallet_account，GET /api/wallet 可能查无账户。

## 3 抢票接口与请求字段

POST /api/tickets/reserve 需要登录，提交 JSON ReserveRequest。成功表示 **实时准入已通过且预占/落单完成**；系统将自动支付并出票，可轮询 orderId。深度风险分析在后台异步更新 RiskProfile，**不回溯本单**。

| 字段 | 类型及约束 | 语义 |
|---|---|---|
| requestId | 非空字符串，最多 80 | 客户端受理幂等号，同号必须同业务参数 |
| userId | 正 Long，不可空 | 必须与 token 用户一致，否则 403 |
| eventSessionId | 非空字符串，最多 36 | 必须匹配 SKU 所属场次 |
| ticketSkuId | 非空字符串，最多 36 | 票档标识 |
| quantity | 整数 1 至 100 | 还要受 SKU 限购与剩余库存约束 |
| deviceId | 非空字符串，最多 100 | 风控上下文和指纹组成项 |

请求示例：

```json
{
  "requestId": "reserve-demo-001",
  "userId": 1,
  "eventSessionId": "替换为场次ID",
  "ticketSkuId": "替换为票档ID",
  "quantity": 1,
  "deviceId": "device-demo-001"
}
```

成功 data 包含 reservationId、orderId、status；新建一般为 **WAITING_PAYMENT**。重放已完成请求返回既有对象身份，状态查询才是后续履约事实。20 次相同请求都返回成功并不表示 20 次有效抢票，应按唯一订单和预占行统计。

## 4 订单钱包与支付接口

| 方法与路径 | 请求 | 结果与限制 |
|---|---|---|
| GET /api/orders | token | 当前用户最近最多 100 条订单，数据库 Map 字段 |
| GET /api/orders/{id} | token、订单 ID | 检查所有者，返回订单并附 tickets |
| GET /api/orders/{id}/trace | token、订单 ID | 检查所有者，返回 Java 工作流记录 |
| POST /api/orders/{id}/cancel | token、订单 ID | 合法状态才能取消，释放数据库预占并挂 RELEASE |
| POST /api/orders/{id}/pay | PaymentRequest | Wallet 兼容支付，非 Demo 正常抢票必经 |
| POST /api/orders/{id}/refund | PaymentRequest | Wallet 退款语义，当前未按原支付渠道分流 |
| GET /api/wallet | token | 当前用户钱包行，可能为空 |

PaymentRequest 只有 paymentRequestId 与 deviceId，均非空，长度分别最多 80、100。amount 与 userId 不由这个支付请求决定，取自已锁定订单和登录态。对相同支付号的重放还核对 orderId、user、type、device，避免请求号被移用。

Wallet 支付可返回 SUCCESS、FAILED、REVIEW、BLOCKED 等持久化交易状态；HTTP/Result 成功并不代表 status 一定 SUCCESS。相同 FAILED 请求重放返回已有失败结果，不会在后来余额增加后自动重新扣款。自动支付使用 AUTO_PAY:orderNo，与手动请求共用 payment_request_id 唯一空间。

主链自动支付不扣钱包，退款却会向钱包加款。这一源码现状在演示时必须说明，不可用“退款成功”推断此前真实发生过同渠道扣款。

## 5 管理接口完整清单

| 方法与路径 | 输入及校验 | 当前行为 |
|---|---|---|
| POST /api/admin/events | name 非空≤150；venue 非空≤200；description≤4000 | 创建 ON_SALE 演出，返回 id |
| POST /api/admin/sessions | eventId 非空；startsAt 非空日期时间 | 创建场次，数据库外键校验演出 |
| POST /api/admin/skus | eventSessionId、name、price、totalStock、purchaseLimit、saleStartTime、saleEndTime | 初始 OFF_SALE，结束时间须晚于开始 |
| PATCH /api/admin/skus/{id} | query status；可选 stock | 调用 CatalogAdminService 更新，非任意字段 patch |
| GET /api/admin/reviews | 无分页参数 | 按创建时间取最近 100 条，不只 PENDING |
| POST /api/admin/reviews/{id}/decision | requestId 非空≤80；action APPROVE 或 REJECT | 审核提交后 APPROVE 触发 attempt |
| GET /api/admin/orders/{id}/risk | 订单 ID | 风险决策行列表 |
| GET /api/admin/orders/{id}/trace | 订单 ID | Java 工作流执行链 |
| GET /api/admin/orders/{id}/audit | 订单 ID | 已持久化审计，不保证完整 Python trace |
| GET /api/admin/rules | 无 | 规则行列表 |
| PUT /api/admin/rules/{code} | RiskRule，含 enabled、weight、config、version | 按 code 和旧 version 更新，无创建新规则语义 |
| POST /api/admin/blacklist | kind、value、seconds 查询参数 | kind 为 user/device/ip，TTL 默认 3600 秒，最大 30 天 |
| POST /api/admin/pools/{name} | core、max 查询参数 | 调整现有命名线程池 |
| GET /api/admin/metrics | 无 | 审计聚合与 Micrometer 指标 |

SKU 创建的 price 最少 0.01，totalStock 最少 0，purchaseLimit 为 1 至 100，name 最多 80。销售窗口由请求输入和服务校验，库存及限购仍有数据库和 Lua 防线。修改已有交易 SKU 时不能把管理接口理解为自由重置历史账本。

规则 weight 要求 0 至 1000，config 非空。DECISION_POLICY 校验 review、block、agentMaxAdjustment、rateLimit 的数值类型与 review>0、block>review、enabled；不是每个参数都具备完整正负边界校验。普通规则要求 feature 字符串和 threshold 数值。更新失败不能假装新版本已生效。

审核 requestId 与支付 requestId 不同；审批动作成功提交后自动支付若失败，HTTP 可能报错但审核状态已改变。客户端应使用原审核请求号查询/重放，而不是换一个动作盲目再次提交。

## 6 运维接口和 Agent 合同

Java 暴露 /actuator/health、/actuator/metrics、/actuator/prometheus。配置公开健康与 Prometheus，管理指标路径另有 ADMIN 校验；实际应结合 MvcConfig 与拦截器，不可默认所有 Actuator 均公开或均需登录。

Python 提供 GET /health 与 POST /api/risk/analyze。分析请求需要 X-Internal-Key，响应直接是六字段 Analysis。

| AnalyzeRequest 字段 | 类型 | 必填与意义 |
|---|---|---|
| order | dict | 必需，当前 Java 主要传 amount |
| userSummary | dict | 必需，当前主要 historyCount |
| deviceSummary | dict | 必需，当前主要 accounts |
| ipSummary | dict | 必需，当前主要 requests |
| paymentSummary | dict | 必需，当前主要 failures |
| features | dict[str,float] | 必需，规则特征 |
| matchedRules | list[str] | 必需，命中规则标签 |
| historicalEvents | list[dict] 或 null | 可选，默认 None；跨场次记录 |
| ticketFlows | list[dict] 或 null | 可选，默认 None；生命周期记录 |
| linkedAccounts | list[dict] 或 null | 可选，默认 None；账号关系 |

旧请求兼容示例，可以省略全部三组历史字段：

```json
{
  "order": {"amount": 100},
  "userSummary": {},
  "deviceSummary": {},
  "ipSummary": {},
  "paymentSummary": {},
  "features": {},
  "matchedRules": []
}
```

| Analysis 字段 | 类型及范围 | Java 使用方式 |
|---|---|---|
| riskLevel | 字符串 | 展示性建议，最终业务 decision 另算 |
| scoreAdjustment | 整数 -20 至 20 | Java 仅在可用时取非负 cap 增量 |
| reasons | 字符串列表，最多 20 条 | 保存分析理由 |
| suggestion | 字符串 | 建议，默认提示 Java 规则权威 |
| confidence | 数值 0 至 1 | 辅助展示，不进入当前分数公式 |
| aiAvailable | 布尔值 | false 时零调分继续 Java 规则 |

最外层 Analysis 的 riskLevel 是 str，内部 AnalystDecision 和报告对等级使用 Literal；不要把两个模型约束混为一谈。顶层 extra=forbid 不等于任意 dict 内部字段都严格限制。非法额外 finalDecision 字段不是兼容扩展。

缺模型密钥时，fallback 为 riskLevel=UNAVAILABLE、scoreAdjustment=0、reasons=["LLM API key is not configured"]、suggestion="Java rules remain authoritative"、confidence=0、aiAvailable=false。执行异常时 reasons 改为 ["LLM unavailable or response failed validation"]。输入 schema 错误 422，密钥错误 401，模型执行异常通常 HTTP 200 的降级结果。缺真实模型 key 能验证合同降级，不代表真实推理已运行。

## 7 数据库总体结构

以下逐表字段由 schema.sql 自动提取，包括列类型、空值和默认/约束。数据库共 21 张表，分为用户目录、交易库存、消息、风控审核、支付票据、工作流审计。只声明了 session→event、sku→session、order→reservation 三处物理外键，其余多为逻辑引用，不能说全表均由外键约束。

在 DDL 中声明 CHECK 不等于已经反查所有现有数据库均有效；实际 MySQL 版本、建表历史和迁移执行情况需要另行验收。TEXT/MEDIUMTEXT 中存 JSON 是应用约定，数据库列本身不是原生 JSON 类型。

## 8 表间关系与唯一性地图

演出到场次、场次到 SKU 为一对多；用户与 SKU 通过 user_purchase 维护配额。意图通过预分配 ID 连接 reservation 与 order，订单再关联风险、审核、支付和票。多数关系由应用维护而非物理外键。一个订单可以有多次风险评估与支付尝试，但只允许一个 PAYMENT 成功业务键和一个 REFUND 成功业务键。

| 不变量 | 主要约束 | 不能单独证明的事情 |
|---|---|---|
| 一请求一订单 | 意图 request_id 主键、reservation request_id 唯一、order reservation_id 唯一 | HTTP 只返回一次 |
| 不超卖 | Lua stock 检查、MySQL 条件减、CHECK | Redis/MySQL 时刻完全一致 |
| 限购 | Lua 用户计数、user_purchase 复合主键及条件增 | 防止所有多账号滥用 |
| 一事件一 Outbox | message_key 唯一 | MQ 不重复投递 |
| 一次业务消费 | group+message_key/business_key、同事务 DONE | afterCommit 后续动作一定成功 |
| 一次成功支付 | payment_request_id 与 success_key 唯一、锁单 | 当前发生了真实资金扣款 |
| 一次有效钱包流水 | transaction_id 唯一、钱包同事务更新 | 自动支付也会生成钱包流水 |
| 不重复出票 | order_id+sequence_no 唯一、PAID 状态 | 已提供实名核销和转让平台 |

## 10 消息合同与任务参数

```json
{
  "orderId": "替换为订单ID",
  "type": "RISK_CHECK",
  "messageKey": "RISK_CHECK:替换为订单ID"
}
```

RISK_CHECK 在预占落单事务登记，语义为**后置深度画像分析**（保留消息名以减少兼容改动）；ISSUE 在成功支付确认事务登记；RELEASE 在正常订单释放事务登记。topic 均为 ticket-events。消费验证正文 type 与 messageKey 一致。RISK_CHECK 消费完成 = RiskProfile 已更新，不改当前订单状态。

| 任务 | 当前周期或条件 | 处理范围 |
|---|---|---|
| Outbox publish | 默认约 1 秒 | 每批最多 50，到期消息领取与发送 |
| compensate | 约 30 秒 | SENT 超 5 分钟未 DONE、FAILED 超 1 小时 |
| 意图恢复 | 约 10 秒 | 每批最多 100，REQUESTED 超 2 分钟 |
| 订单过期 | 约 5 秒 | 每批最多 100，四种可超时状态 |
| 缓存配置 | 约 30 秒 | 刷新 SKU 配置；非任意重置库存 |

这些周期是配置和代码目标，不是硬实时完成承诺。任务队列、锁等待、依赖失败可能增加延迟。没有自动支付 WAITING_PAYMENT 专用重试任务。

## 11 典型问题与核对方式

### 11.1 抢票返回失败但意图存在是否异常

不一定。意图独立提交是恢复设计的一部分。检查 status 是否 REQUESTED、是否有 reservation/order、Redis HELD 是否存在、是否超过恢复阈值。不能见意图就直接加 MySQL 库存，因为落单事务可能已回滚。

### 11.2 为什么支付没有钱包流水

先识别 payment_request_id 是否 AUTO_PAY: 开头。自动确认路径不扣钱包、不写 PAYMENT ledger；WalletService 才产生扣款流水。若自动支付后退款给钱包加款，应作为资金语义限制处理，不是凭空补一条支付流水。

### 11.3 为什么消息 DONE 但订单还在 WAITING_PAYMENT

RISK_CHECK 画像更新完成和 afterCommit 自动支付完成是不同提交、不同语义。检查 payment.auto.failure、日志及支付行；画像消息 DONE 不会也不应再触发支付。

### 11.4 为什么同一 requestId 得到多次成功 HTTP

幂等允许重放返回相同成功结果。以唯一 reservationId/orderId 和数据库行数判断有效业务次数，而非统计 2xx 次数；请求参数变更则应被指纹拒绝。

### 11.5 为什么没有 LLM key 也能返回

这是 fallback 合同，aiAvailable=false、零调分。可验证旧 Java 请求解析与降级，不能证明 Behavior/TicketFlow 已执行真实模型调查。

### 11.6 为什么历史字段有了却没有跨场次证据

Java 当前只装配汇总与特征，不发送历史列表；Python 工具从请求读取而不查数据库。未提供与空记录都有意义，但不存在的证据不会由图自动生成。

### 11.7 为什么修改 schema 后老库没变化

Compose 初始化目录只在首次创建数据目录时执行，Java initialization-mode=never，Flyway 未启用。应对照实际库结构与迁移记录，不能删卷作为常规升级手段。

### 11.8 为什么 Agent 超时后 Java 仍能审核

RiskAgentClient 吞并外部调用异常为 unavailable，完整风险评估按原规则分结束。REVIEW 可开人工单，Agent 的 HTTP 失败不是订单必然 BLOCK。
