# 票务交易与风险调查系统完整结构文档

本文依据 2026年9月17日工作区源码、DDL、配置与现有测试源码整理。它是源码说明，不是本次真实环境验收报告；未重跑的测试、容器状态、吞吐量和模型效果均不作为已验证结论。

## 1 项目定位与阅读范围

这个项目围绕单一票档的预占、订单履约和风险调查展开。用户浏览演出及场次，提交抢票请求后先得到已持久化的订单标识，再通过查询接口观察自动支付确认和出票的推进。

**抢票请求只执行实时准入风控；深度风险分析在交易后异步执行，结果用于更新后续请求使用的风险画像，不回溯影响当前订单。**

Java 后端拥有交易写入权和 RiskProfile 最终写入权。Redis 提供原子库存闸门、限购计数、请求频率、登录态与 RiskProfile 热缓存；MySQL 保存交易事实、Outbox 与 `tb_risk_profile`；RocketMQ 驱动后置深度分析、出票和 Redis 释放。Python risk-agent 是证据调查服务，只有深度评估初判为 REVIEW 时才调用，且**不影响当前订单履约**。前端负责输入、展示、轮询；可提示「后台风险分析中」，但不能阻止当前履约。

当前 Demo 主链在 fast 准入通过后落单为 WAITING_PAYMENT 并自动确认支付，不连接第三方支付。WalletService 与手动 /pay、/refund 仍保留兼容路径，准入同样只走 fast / RiskProfile。

本册解释整体协作。第 2、3 册提供各 100 道面试问答；第 4 册给出接口、完整字段字典和排障细节；第 5 册讨论选择、代价与现有缺口。文中的设计目标与源码现状分开陈述。

## 3 系统边界和两条执行路径

当前请求（同步）：

TicketController → FastRisk（黑名单 / 限流 / RiskProfile / 轻量规则）→ ALLOW/BLOCK → Redis Lua → MySQL CAS → WAITING_PAYMENT Order → AutoPayment → ISSUE → ISSUED

旁路（异步后置画像）：

Order / Outbox `RISK_CHECK` → RocketMQ → TicketEventConsumer（risk 线程池）→ Java Deep Rules → REVIEW? Agent : skip → Java Final Decision → `tb_risk_decision` + `tb_risk_profile` + Redis cache → **仅下一次请求使用**

深度分析消费完成 = 风险画像已落库/已缓存，**不代表「当前订单风控已通过」**——因为当前订单履约不再等待该结果。

Agent 仍可能在 REVIEW 分支同步阻塞 risk 池任务，但不锁住抢票 HTTP，也不改订单状态。

## 4 登录与访问控制

用户通过 /api/user/code 和 /api/user/login 的 Demo 验证码流程获取 token。当前实现依赖 DEMO_LOGIN_ENABLED 开关，不是完整短信网关登录系统；DTO 和表中存在 password，不代表密码登录、哈希存储流程已经实现。新用户默认 USER，当前注册流程不同时创建钱包账户。

RefreshTokenInterceptor 从请求头恢复 Redis 中的用户信息，LoginInterceptor 检查登录，管理接口再要求 ADMIN。订单查询与操作还检查订单所属用户。ReserveRequest 必须提供 userId，Controller 校验其与登录身份相等，不会默默接受替他人下单。

IP 取自 getRemoteAddr，应用配置只信任指定反向代理的转发来源。deviceId 来自客户端，是风控信号而非可信硬件身份证明。共享密钥保护 Java 到 Agent 的入口，Python 未获得交易数据库连接和写交易工具；这是一种代码能力边界，不应夸大为已完成网络层强隔离和生产安全审计。

## 5 抢票请求与持久化意图

请求至少包含 requestId、userId、eventSessionId、ticketSkuId、quantity、deviceId。Controller 先处理已 COMPLETED 请求的重放，校验指纹后返回原 reservation/order；新请求执行 fast 风控、SKU 存在性检查和缓存配置，再创建意图并进入落单事务。

ReservationIntentService.create 使用 REQUIRES_NEW 与 READ_COMMITTED。它先检查已有意图，再锁 SKU、复查并插入 REQUESTED。reservation_id 和 order_id 在意图创建时预分配，不是落单后回填。独立提交的意图保证后续 Redis 成功而主事务失败时仍有可恢复记录。

fingerprint 是对用户、场次、SKU、数量、设备组成的 JSON 序列做 MD5。它用于发现同一个 requestId 被复用于不同业务参数，不承担密码学签名或请求鉴权；IP 不在摘要中。换 requestId 是新请求，能否再次成功由库存和限购决定，不能说指纹可阻止所有重复购买。

## 6 Redis 原子预占与 MySQL 防线

reserve_ticket.lua 在一个原子脚本中检查既有预占指纹、释放状态、数量、开售窗口、用户限购和剩余库存，然后扣 stock、增加用户计数、写 HELD 哈希并加入 pending 有序集合。相关键使用 ticket:{skuId}: 前缀，同一个 SKU 的 hash tag 一致。Redis 服务端 TIME 用于开售判断。

ReservationTransactionService 锁意图后执行 Lua，再用 MySQL 条件 UPDATE 扣 remaining_stock，要求库存足够、SKU 在售且处于销售窗口；tb_user_purchase 的条件增加提供持久化限购。reservation、CREATED order、RISK_CHECK Outbox、意图 COMPLETED 与工作流记录一起提交。数据库失败不会自动回滚已执行的 Lua，因此必须有意图恢复机制。

注意锁的位置：configure 与创建意图时存在 SKU FOR UPDATE；落单阶段不是简单的“先锁 SKU 后 Lua”单一事务图。库存扣减虽然递增 version，但 WHERE 依据库存、状态和时间，未比较旧 version；订单状态迁移则确实比较 status 和 version。两种并发保护不可混称。

InventoryService.configure 只有在 remaining_stock 等于 total_stock 且没有该 SKU 意图记录时才允许初始化 stock。已有交易历史时不会凭总库存重建 Redis；键缺失可导致预占拒绝。当前没有完整停写、对账、重建再开售工具。

## 7 恢复释放与库存一致性

数据库正常释放由 reservation 的 HELD → RELEASED 条件更新守门。只有首次释放才增加 MySQL 库存、减少用户已占数量并登记 RELEASE Outbox；MQ 消费 RELEASE 后执行 Redis release_ticket.lua。Lua 再以 HELD 状态保证只回补一次。重复取消、重复投递和超时竞态必须同时依靠数据库与 Redis 各自的幂等边界。

孤儿恢复是另一条路径。ReservationRecoveryService 锁定超过两分钟仍 REQUESTED 的意图，执行 Redis 释放并把意图标记失败。这类请求的 MySQL 业务事务尚未成功，不能再无条件增加 MySQL 库存，否则会重复补偿。Redis 的 pending 集合记录候选信息；实际 Java 恢复任务以数据库意图扫描为入口。

这是跨系统最终一致性，不是 Redis 和 MySQL 的分布式原子事务。短暂库存差异不自动代表超卖，需要结合成功订单、HELD 数量、释放消息和恢复记录判断。进程崩溃点、租约过期和重复消息是验证重点。

## 8 Outbox 投递和消费

OutboxService.append 要求 MANDATORY 事务。消息正文包括 orderId、type、messageKey；message_key 为 type:orderId，唯一约束限制同一订单同一事件类型只有一行。当前类型只有 RISK_CHECK、ISSUE、RELEASE，目标 topic 为 ticket-events。

Publisher 每批最多领取 50 行，到期 PENDING、RETRY 或 SENDING 可竞争领取。一次领取写入 lease_token 并设置 60 秒租约；发送等待最多 3 秒，只有 SEND_OK 才标记 SENT，状态回写必须匹配租约令牌。失败指数退避，默认到 12 次标为 FAILED；源码的指数上限使退避最大为 256 秒，外层还设 300 秒封顶。

补偿把五分钟没有 DONE 消费记录的 SENT 重新排队，也会将一小时以上的 FAILED 重置重试。SENT 只说明发送确认，DONE 才是该消费者本地事务完成。发送后、写 SENT 前崩溃必然可能重复投递，租约只能协调工作者，无法保证网络传输恰好一次。

TicketEventConsumer 校验消息键与类型，锁订单，再查消费记录；已有记录直接返回，否则插 PROCESSING、执行状态转换与副作用、标 DONE，整体在一个数据库事务里。消费表同时约束 group + message_key 和 group + business_key。ISSUE 还依靠订单 PAID 状态及 order_id + sequence_no 唯一约束防重复电子票。

## 9 Java 风控引擎与策略注册

RiskFeatureService 从 Redis 获取用户、设备、IP 频率和关联账号计数，从 MySQL 获取账户年龄、历史订单取消退款比例、支付失败和已知设备等信息，并存短期特征快照。实时特征不是完整历史调查平台；当前 Java 不装配三组可选历史列表。

RiskRuleEngine 遍历启用规则，向 RiskRuleEvaluatorRegistry 寻找匹配策略，聚合分数及 ruleCode@version 标签。当前主要实现是 GenericThresholdRuleEvaluator，依据 config.feature 与 threshold 等配置进行阈值判断；fast 标记和附加条件控制适用场景。

Registry 拒绝重复策略类；同一规则如果有多个策略同时支持会报错，未匹配策略则跳过。它不是按先后顺序取第一个，也不自动发现任意脚本。RiskContext 包装特征与 fast 标记，但内部 Map 并未做深不可变复制。

DECISION_POLICY 提供 review、block、agentMaxAdjustment、rateLimit。分数达到 block 为 BLOCK，达到 review 为 REVIEW，否则 PASS。fast 处理限流、黑名单与快筛 BLOCK，不调用 Python，也不把 REVIEW 当作同步拒绝。evaluate 保存最终 decision、score、features、matched_rules、agent_analysis 与上下文信息。

## 10 Java 与 Agent 的合同

Java 当前以 Map 装配请求而非专门 AnalyzeRequest Java DTO，Python 使用 Pydantic AnalyzeRequest。七个基础字段必需：order、userSummary、deviceSummary、ipSummary、paymentSummary、features、matchedRules。historicalEvents、ticketFlows、linkedAccounts 均为可选，默认 None，允许旧请求省略。

只有 preliminary=REVIEW 才会调用 RiskAgentClient；连接超时 400 毫秒，读取超时 2 秒。缺内部密钥、HTTP 错误、空结果或 aiAvailable 非 true 会返回 aiAvailable=false、scoreAdjustment=0。Java 使用非负有界调分：增量 = max(0, min(agentMaxAdjustment, scoreAdjustment))，随后重新决定结果，黑名单仍优先。

在阈值和策略配置有效时，Agent 不会把 REVIEW 降为 PASS，只可能保持 REVIEW 或促使 Java 判 BLOCK。Python 的 scoreAdjustment 合同允许 -20 到 20，负数到 Java 会归零。riskLevel、confidence 与自然语言 suggestion 都不是直接执行指令。

Python 无模型密钥或执行异常时返回 HTTP 200 的降级 Analysis；内部鉴权失败为 401，请求格式错误为 422。Java 降级可以继续规则决策，但 REVIEW 不会因为模型不可用而自动放行。

## 11 LangGraph 调查层

图从 START 并行进入 BehaviorInvestigationAgent 与 TicketFlowInvestigationAgent，合流到无工具的 RiskAnalystAgent。Analyst 判断证据是否足够；若不足，指定 behavior 或 transaction 及非空 focus，定向重跑该调查节点，再回到 Analyst。总再调查次数最多 2 次，不是每个 Agent 各 2 次。

每次调查最多 4 次模型迭代，包含最终证据生成轮。一次模型回复可以请求多个工具，因此 4 不是工具总调用次数上限，也不是 token 或整图时长预算。到循环上限仍未输出最终证据会失败降级。再调查达上限会强制收束，这代表流程结束，不保证证据已客观充分。

Behavior 的四个工具分别处理跨场次记录、账号关系、行为时间接近度和处罚历史；TicketFlow 的四个工具处理票生命周期、转让网络、身份变更、退款与入场模式。所有工具从本次请求闭包读取数据，没有联网查库、写订单或支付能力。模型不能自由注册新工具；未知工具名得到错误观察，不执行任意代码。

当前工具 schema 参数为空，执行时使用闭包，模型 arguments 未用于查询，也没有完整的参数校验框架。行为相似是对已有记录做时间接近统计，不是训练好的聚类模型；转让网络是事件观测汇总，不等于确定票的最终持有人。

GraphState 保存两路 evidence、focus、计数与 trace，trace 通过 operator.add 合并。图 compile 没有配置持久化 checkpointer。完整内部报告包含证据和轨迹，但 HTTP 只投影六个字段；Java workflow_checkpoint 表不是 LangGraph 恢复检查点。

## 12 自动支付确认与审核

RISK_CHECK 的 Java 最终 PASS 将订单转 WAITING_PAYMENT，并注册 afterCommit；外层事务提交后在同一个调用线程执行 AutoPaymentService.attempt。AutoPaymentExecutor 是独立 Spring Bean，使用 REQUIRES_NEW，锁订单并检查状态，写 PAYMENT SUCCESS、PAYING → PAID 和 ISSUE Outbox。类名 Executor 不代表线程池异步执行。

支付请求键固定为 AUTO_PAY:orderNo，成功业务键为 PAYMENT:orderId。已有支付记录会校验关联并返回，避免重复创建 ISSUE。订单锁与唯一键共同保护同一订单的并发自动确认。此路径不扣 wallet，不写 PAYMENT ledger，也不调用三方渠道。

人工审核先锁订单再锁审核单，校验未过期、动作、请求号与审核者，条件更新版本。APPROVE 转 WAITING_PAYMENT，REJECT 阻断并释放。AdminController 在 review.decide 事务返回后调用 attempt。因此审核成功与支付成功并非同一事务，接口错误时审核可能已经提交。

已识别的源码缺口：afterCommit 自动支付失败时，订单可能仍停在 WAITING_PAYMENT；`RISK_CHECK` 消费完成只表示画像已更新，不会也不应自动重新支付。现有定时任务没有扫描 WAITING_PAYMENT 重试自动支付。幂等能力不等于持久化重试能力。

## 13 Wallet 兼容支付与退款边界

WalletService.pay 只接受未过期 WAITING_PAYMENT 订单，锁单并核验用户，检查 paymentRequestId 与原请求语义，再执行 **fast 准入**（RiskProfile/黑名单/限流），不再对当前支付调用深度 evaluate 改订单态。成功才条件扣钱包、写 ledger、转 PAID 并登记 ISSUE；余额不足写 FAILED 支付记录且不扣成负数。相同失败请求重放返回原结果，不会变成一次新的扣款尝试。

WalletService.refund 走 REFUNDING → REFUNDED，给钱包增加订单金额、插退款交易和流水、删电子票、释放库存。当前代码没有按原支付渠道区分 AUTO_PAY 与钱包支付：自动支付没有扣钱包，但退款仍可能给已存在的钱包加款；钱包不存在则失败回滚。因此不能将现状描述为闭合的真实资金退款系统。

自动支付执行器内部也没有单独校验 expires_at，而是依赖状态与其他流程检查；与超时任务的临界竞态属于后续正确性验收点。本次只记载源码边界，未改交易逻辑。

## 14 状态机完整迁移表

| 起始状态 | 允许的下一状态 |
|---|---|
| CREATED | WAITING_PAYMENT、RISK_CHECKING（兼容）、CANCELLED、PAY_TIMEOUT |
| RISK_CHECKING | RISK_REVIEW、RISK_BLOCKED、WAITING_PAYMENT、PAY_TIMEOUT（历史态，新主链不进入） |
| RISK_REVIEW | WAITING_PAYMENT、RISK_BLOCKED、PAY_TIMEOUT（历史人工审核兼容） |
| WAITING_PAYMENT | PAYING、PAY_TIMEOUT、CANCELLED |
| PAYING | PAID |
| PAID | ISSUED、REFUNDING |
| ISSUED | REFUNDING |
| REFUNDING | REFUNDED |
| RISK_BLOCKED、PAY_TIMEOUT、CANCELLED、REFUNDED | 当前无后续合法迁移 |

迁移通过 OrderRepository.tryTransition(id, from, version, to) 条件更新；成功后同步更新内存对象。状态机约束合法边，SQL CAS 防止旧状态写覆盖，订单 FOR UPDATE 则协调复合操作。三者承担不同职责。

## 15 可观测性与后台工作

BackgroundJobs 调度 Outbox 投递、发送补偿、孤儿意图恢复、到期订单关闭和缓存配置。TaskPools 分为 outbox、compensation、reservation、timeout、cache、risk，管理接口允许调整线程池。AtomicBoolean 只避免本 JVM 同一任务重叠，不是跨实例分布式锁。

workflow、workflow_node、workflow_checkpoint 保存 Java 执行节点与摘要，audit_log 提供请求响应、token、耗时等存储字段。字段存在不代表 Python 每轮模型调用、每次工具观察和 prompt_version 都已经自动写入；当前 Python 完整 trace 也不通过六字段响应返回。Admin 的 LLM 汇总不能直接当成完整模型成本账单。

Actuator 暴露 health、metrics、prometheus；traceId 用于日志关联。追踪记录辅助排障，不驱动订单合法状态。只依据 workflow 的 SUCCESS 或 RUNNING 判断交易终态可能误读，最终以订单、支付、票和消息事实交叉核对。

## 16 部署配置与数据初始化

Compose 包含 MySQL、Redis、RocketMQ namesrv/broker/topic 初始化任务、risk-agent、Java、Web、Prometheus。MySQL 与 Redis 有健康检查，topic 初始化任务成功退出是正常状态，不能要求它持续 running。默认暴露主机 3307、6379、8082、8080、9090；其余服务通信使用容器网络地址，不能将应用默认 localhost 直接等同于 Compose 可用主机端口。

MySQL 容器把 schema.sql 和 data.sql 挂载到首次初始化目录；已有数据卷不会因为文件改变自动重建或升级。application.yml 的 initialization-mode 为 never；POM 没有启用 Flyway 依赖，db/migration 下的 V100/V101 文件只是迁移材料，不能宣称启动自动执行。

Agent 的 INTERNAL_API_KEY 用于内部鉴权，OPENAI_API_KEY 用于模型供应商，二者不能混用。无真实模型密钥可走 fallback，但这只能验证降级合同，不能证明真实模型质量。文档不复制私有密钥。

## 17 测试边界与阅读源码的方法

Python 测试使用脚本化模型验证合同、工具隔离、循环上限、再调查与降级；Java 测试覆盖规则、状态、Outbox、自动支付及钱包等，真实并发类可能需要 Testcontainers。源码中存在测试、历史报告曾通过，与当前真实 MySQL/Redis/MQ 全链路通过是三种不同证据。

本次文档生成未启动中间件、未重跑交易验收或性能测试，所以删除旧版固定“75 tests”作为当前事实的写法。若准备面试，应给出实际执行时间、命令、报告及跳过原因，而不是背一个已经过期的测试数量。

读源码建议沿四条线进行：TicketController 到两个 Reservation Service 理解同步受理；OutboxService 到 Publisher、Consumer 理解异步推进；RiskDecisionService 到 Registry、RiskAgentClient 理解终裁；AutoPaymentExecutor 与 WalletService 对照理解 Demo 履约和资金兼容路径。
