# E/F执行边界与验收计划

E保留16桶和既有表头，新增allocation_item明细，不改旧数据。协议3的Redis marker保存16分量向量；先验证全部条件再修改库存，Java校验sum(quantity)、16桶范围和指纹，SQL按桶号顺序CAS并在同一事务持久表头/明细/预占/订单/Outbox。释放、退款经原订单状态机，SQL表头released只裁决一次，Redis状态只释放一次；Armory恢复从权威明细重建向量和原支付期限。

V113只附加SKU单次限额、持久协议开关和明细表。单次限额在SKU（因此按其所属场次隔离）上配置，1至100，只允许首次装配且无交易之前；本轮没有新增场次级默认值继承。默认100保持旧请求上限，累计限购不变。没有重写旧allocation主键、迁移已售库存或使用单SKU MySQL库存行锁。

新功能独立vector-reservations=false；启用要求B/C兼容且持久模式一致，必须全实例升级/排空后审核激活。旧单桶marker/分配表头仍可释放和恢复；向量表头bucket_id=-1，明细丢失拒绝恢复，绝不猜测分配。

售罄不是持久全局锁存：只有Lua确认所有可用桶为0后发出扫描提示。扫描有界，先持有Armory版本屏障和attempt锁，再由同槽Lua复核0库存并写本attempt墓碑；释放先发生则不误判，墓碑先发生则释放不能复活旧attempt。HELD marker和已完成Lua turn不清理。已发布的后序资格不能直接终态而留下游标空洞，会先写墓碑、让出租约，待前序安全完成再推进。WAITING截止仍先按B裁决，不延长5秒。

## 测试分层

- E L1：受影响编译、跨桶CAS/回滚/幂等释放并发；独立Redis小规模8并发脚本验证原子分配、库存不足、丢桶、错误类型和售罄/释放。
- E L2：真实Redis/MySQL、数量>单桶、明细提交/回滚、Armory恢复、取消释放、售罄和新attempt。
- F：统一全量本地回归，条件依赖项如实报告；真实MySQL/Redis集成；真正子JVM在Lua成功/SQL未提交点被终止，并由两个独立worker JVM恢复；最后进行一次A/B交错对照。

外部Agent、真实支付网关及出票不调用；既有相关状态机/幂等测试使用本地替身，不改生产业务逻辑。

## 统一性能对照

同一候选代码，仅切vector-reservations和其持久匹配位；B/C/D均开启。A旧单桶分配，B向量分配；quantity=1、充足库存，使两组具备相同业务可行性。不是“旧易失202”和“新可靠202”的等价比较，也不是5000 TPS容量测试。

计划A→B→B→A→A→B，每轮新JVM、独立schema/Redis DB，同场次100库存，3个预热请求后50个唯一请求、客户端并发10，用户PASS/REVIEW交错。预热、4次幂等重试单列，不计入50个初始POST。保留实际1000/s入口限流、512容量、活动4、sale4和原连接池。

采集网络POST实际QPS/202/429/503、HELD成功TPS及窗口、WAITING/PROCESSING和HELD端到端延迟、资格/Lua方法耗时、队列终态、Hikari采样、GC/CPU、数据库锁等待采样。端到端以数据库登记时间为起点，完成查询采样存在至多约200ms观察误差，记录DB/宿主时钟校准往返；不能将包含关系P95相加。客户端与服务端同机/同测试JVM，结果不作为独立发压容量上限。

每轮JFR、埋点和数据库低频采样保持一致；原始任务/响应/资源/JFR保存。数据库锁采样行数不是独立等待事件数。每轮等待全部已登记任务终态、库存/订单/意图/租约一致，否则停止；不以快速拒绝提高数字。

资源门槛仍至少1GiB可用内存、1GiB空闲磁盘；不扩容容器、线程池、限流或连接池。测试过程有界超时和归属清理，只结束本轮进程/临时数据。旧Docker容器、卷和网络不做清理/重启。已安装镜像只读预检，测试若需要新资源只能属于本轮。

预期开销：E集成约2分钟；双JVM恢复约1至2分钟；全量回归取决于原有条件集成环境；六轮性能对照约每轮1至2分钟。任一资源、正确性或清理异常停止，先定位，不自动增超时或追加轮次。

默认开关保持关闭，无论性能是否改善都不自动上线。若向量协议未稳定改善性能，只交付正确性与代价，不叠加其他调优。
