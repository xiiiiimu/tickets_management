# V2 首轮性能基线（2026-10-29，优化前）

本报告先记录实际基线，再选择单项最小优化。不是上线性能验收。

原始数据：`performance/results/reservation-v2-20261029_030736/`；每个正式轮次保留请求 JSON、Prometheus 前后快照、SQL digest 与库存证明。统计脚本：`performance/analyze_reservation_pipeline.py`。

## QPS 与 TPS 必须同时看

| 负载 | 实现 | 抢票 POST QPS 中位数 | 可靠预占 TPS 中位数 | HTTP P50 / P95 / P99（秒） | 三轮成功订单 |
|---|---|---:|---:|---|---:|
| 全有效、充足库存 | 原链路 | 4.52 | 4.50 | 5.650 / 14.699 / 16.324 | 480 |
| 全有效、充足库存 | V2 | 7.53 | 3.08 | 3.462 / 7.247 / 8.211 | 480 |
| 96 PASS / 40 REVIEW / 24 BLOCK | 原链路 | 8.51 | 7.21 | 3.671 / 5.824 / 6.703 | 408 |
| 96 PASS / 40 REVIEW / 24 BLOCK | V2 | 9.26 | 2.51 | 2.984 / 5.124 / 7.139 | 408 |

P50/P95/P99 是三轮各自分位数的中位数，非合并全部请求后的分位数。QPS 分母是160次抢票提交返回所需时间；TPS 分母是从提交开始到最终可靠成功得到确认所需时间。HTTP 202 只计受理，不计成功预占。

V2 的受理 QPS 更高，但本组端到端可靠预占 TPS 更低，不能称为整体性能提升。正式轮次全部库存核验通过：16桶余额逐桶与 Redis 相同，订单数量等于实际扣减数量；售罄为0，混合组每轮24个预置 BLOCK不扣库存。正式轮次未出现额外错误；预热/工具调试失败全部保留，不混入正式统计。

## 方法与可比性

两组均开启 Armory、同一 JDK21（Java8目标代码）、Xms128m/Xmx384m、SerialGC、Hikari10、32个抢票提交并发、160逻辑请求、单SKU16桶总库存1000。每轮新场次/SKU/用户/设备/requestId；用户独立 loopback 源IP，未修改11条现有规则的阈值。混合组通过真实设备账户滑窗与真实BLOCK画像构造，不用固定PASS替代风控。

旧基线从任务开始前的完整工作树源码快照独立构建，不拿 Git HEAD 覆盖原有开发成果，也不使用来源不确定的旧JAR。所有轮次后台支付/出票/MQ关闭，排除完整履约干扰；V2持久调度与摘要维护仍运行，是新链路本身的成本。

V2 原生需要 GET 查询结果，本组包含这些额外查询；因此是包含各自协议的端到端比较，不是完全相同数量的HTTP请求。另行增加低频提交后计数器观察组，查询详情放在计时外，隔离这部分成本。查询接口QPS和次数由原始记录/专属SQL digest单列，禁止和抢票POST QPS混算。

单机 Windows / Docker Desktop 的磁盘和JIT波动明显，例如旧链路全有效三轮TPS约3.51、4.50、9.30。只有三轮，不作稳定生产容量外推。历史约9.52 QPS的负载、数据、持久化、后台消费及环境不同，仅作背景，不能直接算提升百分比。

## 按证据排序的瓶颈候选

1. **全局协调行持有连接并串行化受理与领取。** V2全有效前两轮，`SELECT * FROM tb_reservation_dispatch WHERE id=? FOR UPDATE` 分别执行331/339次，数据库累计执行时间约165848/129756ms；主键点查本身简单，结合代码可推断协调锁竞争是强候选。该值含执行和等待，不等于精确InnoDB行锁等待时间；短时锁采样未捕获等待，不能伪称已经测得纯锁等待。受理事务在此锁内还做查重、限购guard准备、插入任务与提交，32个HTTP请求可占满Hikari等待同一行，影响出队。
2. **连接获取与事务提交成本。** 同两轮Hikari获取连接均值约174/121ms，每轮约3810/3731次获取；最终预占事务均值约285/251ms。旧链路也有明显连接池等待。不能通过只增大池容量来证明问题解决，可能让更多连接等待同一协调锁。
3. **冷用户历史摘要重建与定时维护。** 本组用户首次出现，没有大历史；摘要需要真实构建，不能获得热缓存收益。维护与调度共用默认定时线程是额外候选，尚不能凭代码认定其比协调行更严重。
4. **状态查询与多次门禁开销。** V2查询流量会争抢同一MySQL池；runtime gate虽然不再SUM16桶且缓存manifest解析，但保留三道并发边界，不能为提高QPS直接删Gate。可继续审计不变配置缓存和静态SKU查询合并的安全等价方案。

## 第一项最小优化

先限制每实例同时进入“受理协调事务”的竞争者，等待发生在获取数据库连接之前。数据库全局容量、唯一约束、版本Fence、优先级选择、领取租约、原16桶Lua和最终事务全部保持；不以快速拒绝伪造提升。该限制只管理尚未被可靠受理的HTTP调用，不替代持久队列。

优化后必须重新报告POST QPS、真实成功预占TPS、P95/P99、错误/拒绝数量、连接池与SQL指标，并继续验证多实例全局边界和库存一致性。如果仅QPS提高而成功率或TPS变差，不算达标。

### 实验结果与回退

限并发实验：`performance/results/reservation-v2-20261029_051939/`，低频计数器观察模式。全有效组三轮，旧链路POST QPS中位数约5.99、可靠TPS约5.91；实验版V2约4.53 QPS、3.44 TPS，均480个可靠订单。未证明该改动改善QPS，因此已回退，而不是把资源限制包装成优化。

此组与前面带轮询的原型基线有观察方式和宿主机波动差异，不能把两组差值完全归因于限并发。归档实验JAR及源码：`.tmp/architecture-rebuild-20261028/admission-throttle-experiment.jar`、`admission-throttle-experiment-source.zip`；精确SHA见同目录实验JSON。最终版本另行以相同计数器观察方式重测，不混合候选版本统计。
